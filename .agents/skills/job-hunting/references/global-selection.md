# Global vacancy selection for student-stack campaigns

Use this phase to build the shared vacancy pool. Read student-position.md only when assessing an actual student. Read token-policy.md before configuring or invoking token-consuming work.

Inputs: the complete selected source/company manifest, existing populated DB stacks and their descriptions, explicit common selection rules, saved vacancy observations, and the approved inference policy. Do not request/use a student's CV, contacts, salary preferences or application history to decide which roles exist in the shared pool.

1. Resolve existing stacks and selected student membership. Missing descriptions require configuration; unselected stacks and stacks without selected students do not create work.
2. Process every source/company in the frozen manifest. Record unsupported, inaccessible, partial and forbidden sources explicitly. Never open LinkedIn or lnkd.in, even if it is the only source.
3. Apply decisive cheap checks from configured rules, then extract survivors/uncertain cases into full readable posting text. Follow the actual wording in the shared skill and DB stack descriptions; do not substitute the standalone profile filter or a second set of title/keyword rules. Mandatory rules are not fuzzy scoring preferences.
4. Checkpoint raw posting text and source evidence for recovery. Remove image/video/embed payloads and page chrome; preserve substantive job requirements. Record completeness, content hash and extraction version where supported; report missing metadata rather than claiming completeness. This is audit data, not a canonical vacancy insert.
5. Evaluate common global rules and each selected stack against saved descriptions. Only roles passing every applicable common rule and matching at least one stack enter `noco.vacancies`, with their full body and matched-stack links. One vacancy may match several stacks: keep one vacancy row and every accepted link in `noco.vacancy_stacks`; never force one primary stack or copy the vacancy per stack. Excluded, review-only and missing-description observations remain audit data, with no vacancy row. Summaries are optional derivatives, never replacements for the accepted full description.
6. Finalize the shared pool only after every source target is terminal. Fully inspected accepted vacancies remain usable when another page of their source failed; report that source as partial and preserve the missing-page evidence. Incomplete individual postings remain reviewable.

Edit shared rules in [vacancy-selection/SKILL.md](../../vacancy-selection/SKILL.md). Both this workflow and the external-responses classifier read that file; it is the sole global-rule authoring location. Existing stack requirements remain in noco.stacks.stack_description. Do not duplicate shared rules in SQL or hardcode them into keyword branches. A rule needing individual authorization/residence belongs in student consideration. HTML comments/examples in the rule file are inactive.

Outputs: canonical vacancy IDs, complete normalized description/version, employer/source provenance, per-stack decisions, common-rule decisions and a complete source audit.

Save bodies before exposing accepted roles. Reuse existing valid descriptions and content-bound decisions; do not sweep or extract again for each student. Keep posting identity separate from navigable URL; title/company similarity alone is not proof of a duplicate.

This collection command returns the saved pool and collection report without creating application batches or filling/submitting forms. When the overall task already authorizes applications, continue into the separate matching, preparation and application commands after collection completes; this stage boundary is not another approval checkpoint or an end-of-turn requirement. Collection does not use the standalone candidate-profile filter or per-student sent-history list to remove roles from the shared pool. A discovery adapter may follow an official ATS posting to extract the job description; a search-only request still does not authorize applications.

## Current SQL execution path

For a Codex-assisted source repair campaign, use `scan --reasoner codex --concurrency 1 --max-pages 200 --source-timeout-seconds 900 --await-review`. Inspect the reported investigation request, not the entire repository. Use one Sol worker at a time. Supply a request-bound proposal through the session bridge and resume; never assemble a replacement crawl through temporary scripts. Prefer a verified existing engine or recipe configuration before creating code. A generated engine must pass the framework's fixtures and complete live extraction checks before its source binding is saved. Source-specific navigation belongs in SQL recipes/engine artifacts, not this skill. Registration and verification remain coverage gaps. Never infer a complete empty board from a loading widget or missing controls.

After every source has a terminal outcome, classify the saved descriptions across all selected stacks using the current shared rules. Do not label paused investigations or pending classification as zero matches. Report automatic replay, Sol assistance and blocked coverage separately. The SQL source recipe stores the engine reference; vacancy provenance records the same extraction version and actual URLs.

Use `external:responses scan --company-ids IDS --db-stacks IDS --run ID` for repeatable SQL collection. It freezes exact company scope, loads verified recipes/current decisions, reuses compatible complete searches younger than seven days, saves accepted roles and writes one Markdown report. `--force-refresh` fetches listings again; `--resume` retains scope and observation times. Paid AI defaults off; pending classifications are not no-match results. See the [feature entry point](../../../../src/features/external-responses/README.md) and [collection contract](../../../../src/features/external-responses/vacancy_collection/README.md).

`scope` → `collect` → `classify` → `report-collection` remain independent commands; collection never calls applications.

- `collect` / `saveCollection`: saves observations and source coverage to `noco.collection_runs`; it creates no canonical vacancy rows. Raw page checkpoints are recovery/audit data.
- `classify --collection-run RUN_ID` / `saveClassification`: loads that saved run, reads the shared rule file, then atomically writes accepted descriptions to `noco.vacancies`, their matched links to `noco.vacancy_stacks`, and all rule/stack decisions to `noco.collection_runs.classification`.
- `report-collection`: exports coverage and selection decisions without applying. SQL-backed classification is the required save step; running the Python sweep or exporting a JSON shortlist alone is not SQL persistence. Report failed/uncertain saves and reconcile by run ID before retrying; do not label them saved.

The job-hunting strategy is only an injected discovery adapter. Its board sweep does not implement SQL persistence or application authorization. Do not insert vacancies directly or bypass the classifier. `--offline` does not prove a live SQL save. The current implementation classifies after collection; it does not yet classify and promote each posting while crawling.

The normal assessor returns global and all-stack decisions in one call per uncached posting. Exact cache hits make no AI call; changes to full semantic inputs, rules, stacks, extraction or assessment policy invalidate them. Existing global/stack persistence guards still apply. All source targets must have terminal outcomes; partial/inaccessible outcomes remain coverage gaps. Vacancy market follows description language (English -> Global; Russian -> Ru; ambiguous -> unknown), overriding older company-jurisdiction assumptions. Telegram routes are saved for later processing. Student-market routing is enforced by the sequential application workflow, outside collection.

If the standalone API is unconfigured, report that limitation. An explicit `classify --assessments FILE` review adapter is available for decisions made in the dialog or by a person; it requires exact collection/rule hashes and literal evidence and uses the same accepted-only SQL path. Label `assistant_session` or `human` provenance. This verifies crawling and persistence, not unattended model classification; do not fabricate API usage or token measurements.

## Deterministic work before Sol

Run configured title/publication checks first, then exact identities, content/metadata hashes and compatible decision reuse. Recalculate date eligibility with code: crossing midnight does not itself invalidate a semantic assessment. Never use fuzzy similarity or technology words alone to approve a role. Sol medium handles unresolved shared/multi-stack meaning; Sol high handles unfamiliar source investigation/engine development. No automatic Astra second opinion or paid API fallback. Oversized complete descriptions remain pending rather than truncated. Cold benchmarks deliberately bypass historical state; normal scans retain verified recipe/cache reuse.
