# Telegram ID ученика

Вход: `noco.clients.telegram_personal_chat_id` (существующее поле с `@username`).
Выход: `noco.clients.client_tg_id`, точный положительный ID пользователя в виде текста.
Никакие другие поля ученика не меняются. Группы, каналы, боты и удалённые пользователи отклоняются.
Поиск по username определяет его текущего владельца; это не подтверждение личности ученика.

SQL-триггер передаёт только `clients.id` через `NOTIFY unicorn_client_tg_id` после commit.
Unicorn держит отдельное соединение `LISTEN`, разрешает username через существующую
серверную GramJS-сессию и записывает ID условным UPDATE: контакт должен остаться
тем же, ID — пустым, ученик — не удалённым. Повторный сигнал безопасен.
Смена username при заполненном ID не заменяет и не очищает ID.

Новых таблиц, колонок, файлов сессий, истории запросов и внешних сообщений нет.
Ожидающие повторы живут в памяти. После подключения/переподключения выполняется
проверка старых незаполненных записей страницами по 100, затем работа идёт только
по событиям. Периодического сканирования Clients нет.
Не найденный/невалидный username повторно проверяется при изменении username
или восстановлении подключения. Временные ошибки повторяются через
1,5–30 секунд; обязательный FLOOD_WAIT соблюдается полностью для всей очереди.
Между поисками — не менее 250 мс. Каждый поиск ограничен 20 секундами.
В логи попадают только ID записи и фиксированный код результата/ошибки.

## Выпуск (отдельное согласование)

1. Проверить существующее соответствие колонок, права и серверную GramJS-сессию
   (`main_messenger_telegram_session` либо существующий reporting session file).
   Модуль не запрашивает телефон/коды и не создаёт авторизацию.
2. Согласованно применить `src/integrations/postgres/telegram-client-id/001-client-id.up.sql`.
   Она добавляет только функцию/триггер и узкие права приложения, данные не заполняет.
3. Выложить код и включить `TELEGRAM_CLIENT_ID_ENABLED=1` на Unicorn Render.
   Это включает запись ID и для уже существующих подходящих учеников.
4. Проверить один заранее согласованный пример: сохранение строки, событие,
   заполнение ID, сохранность прочих полей. Проследить безопасные логи.

Отключение: убрать флаг и перезапустить Unicorn. Down-миграция удаляет только
функцию/триггер, оставляя полученные ID и существующие права.

Локальные проверки: `node --test src/features/telegram-client-id/*.test.mts`.
Для изолированного PostgreSQL-прогона указать `TELEGRAM_ID_TEST_PG_BIN` — каталог
с локальными `initdb.exe`/`pg_ctl.exe`. Тест создаёт отдельную временную БД на D:,
Telegram не вызывает и рабочую SQL не использует.
