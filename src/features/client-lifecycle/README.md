# Clients / TAS-143

Уведомления об изменениях статуса ученика и напоминания по согласованному ТЗ.
Сообщения формируются фиксированными шаблонами, без генерации моделью.
Модуль по умолчанию выключен; публикация кода сама по себе не включает отправки.

## Состав

- `policy.ts` — условия отправки, пропуска и ошибки данных; без SQL и HTTP.
- `templates.ts` — тексты сообщений с настройками, переданными снаружи.
- `postgres-settings.mts` — чтение общей настройки из PostgreSQL для backend и CLI.
- `worker.ts` — сохранённый уникальный захват перед внешней отправкой.
- `postgres-store.mts` — чтение состояния и собственный журнал обработки.
- `pass.mts` — обработка событий и ежедневной проверки с сохранением прогресса.
- `runtime.mts` — запуск в существующем backend, без отдельного сервиса или Cron.
- `sender.mts` — существующий Telegram-адаптер и отдельная обработка ошибок.

Ошибочное событие не блокирует остальные. Получатель сообщения определяется
данными конкретного ученика; запасной рабочий получатель не подставляется.
Чат выбирается по непустому `secured_general_chat_id`, иначе по исходному
`telegram_general_chat_id`. Перед захватом отправки тот же выбор повторно
проверяется под блокировкой строки; смена чата отклоняет устаревший план.

## Расписание и повторная обработка

Смена статусов проверяется каждые пять секунд после окончания предыдущего прохода.
Ежедневная проверка начинается один раз в окне 19:00–19:59 по Москве.
Начатая проверка продолжается после перезапуска. Если процесс был выключен всё
окно, новая проверка начинается в следующее окно, а не произвольно ночью.
Интервал напоминаний отсчитывается от подтверждённой отправки.

Автоматические отправки делят с уведомлениями LinkLab один сохранённый SQL-интервал
5 секунд, без случайных задержек. Занятый интервал возвращает `deferred`, не
поглощая событие и не останавливая обработчик. Перезапуск не сбрасывает ожидание.
Telegram 429 сохраняет срок повтора конкретного сообщения по `retry_after`.
До установки нового кода нужна отдельная миграция
[`notification-pacing/001-pacing.up.sql`](../../integrations/postgres/notification-pacing/README.md).
Она не включает рассылки. Общие ответы бота и CV-переходы не меняются.

Принятые отправки не повторяются. Неизвестный результат не повторяется вслепую:
Telegram не гарантирует идемпотентность. Явный отказ учитывает срок повторной
попытки; исправление неполных данных не поглощает событие ученика.

## Настройка и проверки

Пустой пример дополнительных настроек — [.env.clients.example](../../../.env.clients.example).
Рабочие секреты, адресаты и ссылки в пример не включены.
Ссылки, контакт поддержки, пароль приветствия и адресат ошибок хранятся одной
служебной записью PostgreSQL. Миграция `004-notification-settings.up.sql` создаёт
пустую таблицу; роль приложения получает только чтение. Значения задаются отдельно,
не входят в Git и не записываются в журнал. Настройка проверяется при запуске
включённого backend или CLI; после её изменения backend нужно перезапустить.
При выключенной функции таблица не читается. Подстановки из ENV нет.
Установка миграций, совместимых потребителей и первоначальное включение —
отдельные операции. История старых переходов автоматически не рассылается.
При отключении журнал сохраняется; рабочие данные не восстанавливаются поверх текущих.

- `npm run clients:test` — изолированные проверки с подменой внешних отправок.
- `npm run clients:check` — предварительный расчёт без отправки по умолчанию.

Тесты используют искусственные данные и настройки.
Контракт завершения CV описан в [дополнении](../../../docs/resume-workflow-tas143.md).
