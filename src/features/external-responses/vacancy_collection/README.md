## Contract

Quota recovery (2026-10-03): transient quota-read failures pause admission and retry at most twice (1s/2s backoff, 5s per quota RPC). Scan and Sol dispatch await recovery rather than abandoning their checkpoint on the first lost read. Existing in-flight work may continue only during this bounded freshness interval; no generation is restarted. Exhausted retries, authentication failure, missing/invalid readings, changed/reset windows, decreases or the hard limit still cancel owned work. Structured diagnostics retain only the error category, RPC method/code and HTTP status; never upstream messages or account data. Recovery preserves the original baseline/high-water mark. The legacy immediate-cancellation behavior on the first transport error is superseded.

`scan --budget-campaign DIR --concurrency 1 --classification cached` attaches the existing quota watchdog to the normal SQL workflow. `DIR` must contain an explicitly approved `budget.json`; no policy is created/reset by scan. Preflight must pass before SQL campaign writes or browser launch. The watcher closes only this scan's browser on a stop, and reader/attempt admission failures use the fatal collection checkpoint path rather than reporting an inaccessible company. Resume binds the same policy hash. Paid API mode is unavailable with this guard; sequential Sol handoffs use the existing separately guarded worker. Freshness reuse and cached decisions still retain their original evidence/timestamps. A missing, stale or stopped quota prevents live work; reporting remains independently callable.

`scan --reasoner codex --concurrency 1 --max-pages 200 --source-timeout-seconds 900` enables the session bridge. Paid API classification cannot be combined with this pilot. The first pass reserves repair capacity (at most 40 reader calls); replay and investigation repairs share the 200-call / 15-minute active-crawl budget. Codex thinking/paused time is separate, never billed as crawl time.

An unfamiliar public source creates an immutable request under the run's `investigations/` directory. Sol (`gpt-6-sol`) writes `<request-id>.proposal.json` using the request/source IDs and either a verified recipe/engine proposal or a reasoned `defer`. Resume the exact original command plus `--resume`. Completed source snapshots keep their original observations; only pending sources advance. At most two repair candidates are allowed. A pending investigation cannot finalize the collection or authorize classification/applications. No API call occurs merely because `--reasoner codex` is selected.

Use `inspect-source --request FILE --url URL --browser-driver patchright` for additional public-page evidence. Optional `--steps FILE` and `--extraction FILE` pass the same constrained reader options as replay. This command shares the collection lock, records read intent before navigation, and writes `<request-id>.inspections.json`. Resume incorporates those actions and deducts their calls/time from the source's remaining repair budget. An interrupted diagnostic read keeps its reserved time; it cannot silently authorize unlimited new reads. Inspection never persists a vacancy, registers an account or submits a form. Do not replace this command with unmeasured temporary browser scripts.

Normal reruns retain already-inspected partial findings for a compatible source whose investigation is explicitly deferred/exhausted, for at most seven days. The source stays **partial/paused**, never complete or freshly searched; original timestamps and gaps remain. `--force-refresh` retries these engine gaps. Authentication/CAPTCHA reviews still need their separate explicit retry. A pending investigation cannot reuse an older complete snapshot as if the new failure had not happened.

Engines live in [engines/README.md](engines/README.md); SQL recipes bind engine ID/version/content hash to a source. Generated JavaScript runs in QuickJS with no host I/O, and can return only checked collection plans/extractions. Framework fixtures and complete live evidence are required before promotion. The previous SQL recipe remains in the new recipe's `previous` field for rollback. Vacancy source metadata records the collection run, recipe revision and engine reference. Code/fixtures remain local feature artifacts; this workflow never commits or pushes Git.

The future API reasoner is an injected interface requiring explicit approval/configuration; it is not wired to a paid provider in this pilot. Classification continues to use existing reviewed-assessment files and exact decision reuse.

`scan --concurrency 1` caps this campaign at one source/repair worker; allowed values are 1–3, existing default 3. The selected limit is part of resumable run configuration. Selecting one application student must not narrow the shared collection's populated stack scope.

`scan --max-pages 200 --source-timeout-seconds 900` explicitly extends a large source to 200 reader calls and fifteen minutes. Defaults remain 24 reads/five minutes; time is bounded to 1–1800 seconds. Replay and repair share both budgets. The time budget is part of the run fingerprint: extending an already completed scan requires a new run rather than changing its original evidence. A read already in progress retains its own navigation timeout.

`scanCollection({runId,sources,scope,memories,force,maxPages,hints?,retryReviews?}, {reader,loadRun,action,onAttempt?})` composes source execution with existing normalization. Dependencies supply SQL snapshots, page reads and durable action checkpoints. It caps source workers at three, drains them on failure and attaches completed source results to an interrupted error. `scan-cli.ts` owns I/O, the existing collection lock, database/browser preflight, persistence, classification and reporting. Use `scan --company-ids IDS --db-stacks IDS --run ID`; all-company work requires `--all-companies` explicitly. No unsupported company is replaced.

`collectVacancies({runId,sources,scope}, {strategy,checkpointPositions?})` returns a `VacancyCollection` containing raw observations, provenance, scope and an outcome for every source. The injected checkpoint callback is audit-only. Source bindings/navigation are validated before it runs; persistence failure aborts and drains workers rather than becoming a website failure. Final-result-only strategies remain compatible.

Await all sources before returning; never stop when one student/stack has enough vacancies. Duplicate posting URLs merge provenance and explicit application destinations. Missing descriptions remain audit findings for classification review. An empty DB stack scope invokes no crawler. Never open LinkedIn/lnkd.in, including redirects.

`collectionIssues` reports structural blockers: missing/duplicate/unexpected source outcomes, invalid terminal states or invalid manifest. Partial/unavailable sources are terminal outcomes; their complete accepted vacancies remain usable. `collectionCoverageGaps` preserves unsuccessful/partial coverage and registry gaps for reporting. A synthesized missing audit has `terminal: false` and cannot authorize applications. Neither a failed page nor absence from a partial scan establishes vacancy closure.

## Crawling and source review

Title routing is configured in the existing `vacancy-selection/SKILL.md` `title-precheck-json.routing` block. Only selected, populated SQL stacks are candidates. The first matching route group wins; matches within that group are combined and intersected with the frozen campaign scope. Testing takes precedence over language/fullstack words; inactive DevOps/QA/PM and unsupported languages never create pending description work. Generic software/backend titles retain the relevant selected candidates until their full descriptions resolve the stack. Navigation controls are not posting titles.

Observations carry `titleRouting.candidateStackIds`, `policyHash` and `scopeHash` in existing collection/run JSON (including the SQL run audit). This is provisional routing, not accepted vacancy membership. Current rules recompute routing on reuse/classification. Only accepted full-description assessments write canonical SQL vacancies and their final multi-stack membership; no new table or migration is involved.

Website/dialog strategies live in `discover.ts`; the job-hunting adapter is in `strategies/job-hunting.ts`. Inject `PageReader` for fixtures/replacement. Website discovery has a hard maximum of three workers, with bounded pages and existing per-host pacing. CLI collection/discovery runs share the existing exclusive workspace lock at `storage/external-responses/candidates/shared-vacancy-collection/application.lock`, including custom `--storage` invocations. A second CLI cannot allocate another three workers. Direct API callers must serialize campaigns; shared ownership with HH/other machines is still deferred. No HH code was changed.

`page-reader.ts` detects explicit listing login/registration walls, excluding ordinary optional login links and application-only registration. `source-reviews.ts` exposes injected `pending`, `queue`, and `resolve` operations. The CLI immediately stores confirmed gates under `storage/external-responses/source-reviews/`; later runs skip pending sources, preserve evidence and continue other sources. Final SQL run audit stores the same access-gate evidence. Review write failures abort collection. After resolving access manually, call `resolve(source)` (or mark the corresponding record `status: "resolved"`) and start a new run. No accounts or messages are created automatically. This local queue is not a distributed SQL task queue.

Generic dynamic controls are bounded; remaining pages/controls are reported as partial. Page extraction preserves full posting text without media/script payloads. Specific sites can still require an adapter; generic detection does not promise universal coverage.

`source-recovery.ts` permits one same-origin homepage entry after an explicitly HTTP 404/410 custom listing URL. Follow only observed career links from that page, within the existing shared page/time budget. Never guess another company domain, visit a shared ATS vendor homepage, bypass an access gate or add a replacement company. A verified complete feed becomes the next recipe entry. If alternate extraction fails to reconcile previously inspected roles, preserve those roles and partial coverage; successful extraction of a different job cannot erase earlier results or prove complete coverage. The source-generalization suite varies hosts, paths and DOM shapes and needs no AI.

Public platform readers support Ashby, Greenhouse, Lever, Recruitee, SmartRecruiters and Workable (see its reader contract above). SmartRecruiters listing pages expose only official listing metadata; pagination and every retained posting detail are separate budgeted `PageReader` reads, so title/publication prechecks run before detail fetches. A missing page, malformed count, missing description or absent actual apply URL remains partial. Workday has no dedicated completeness adapter: generic bounded browser evidence may be retained, but it must not be reported complete without a verified source-specific contract. Existing application-stage platform exclusions remain independent of public listing support.

Before an individual detail page is opened, `title-precheck.ts` applies the deterministic `title-precheck-json` block from the shared vacancy-selection skill. Only configured role families continue; other posting titles and disallowed seniorities are rejected. Generic view/apply links and pagination/category controls remain navigable, but cannot masquerade as posting titles. Development, operations, testing and management recognition is not SQL stack acceptance. Forward-deployed and AI product engineering continue for description verification. Website, scoped skill and scoped dialog collection use this gate; complete ATS feeds are filtered after their single feed read. Audit retains compact title/URL/reason evidence. The same gate runs before independent classification, cache lookup and review packets, so legacy saved noise does not spend AI calls.

Title-filtered `complete` means complete listing traversal for the recorded stack descriptions and selection-rule hash. That scope hash is stored in the collection and source snapshot; a changed rule, selected stack or stack description cannot reuse filtered completeness or resume an older bound attempt. A legacy all-vacancy complete snapshot may be reused only after applying the current precheck. Prior title rejections are not reopened for closure reconciliation, and HTTP-validator reconstruction from accepted-only positions is disabled. Reports show retained discoveries and title-rejected observations separately.

Named developer/engineer links on a public Notion careers site are followed within the same host and page budget. Role details still require substantive application text before classification; the known source supplies the company identity. Unrelated Notion pages and cross-host links are not inferred as job postings. Covered by the Notion navigation and browser fixtures.

Clear only inputs explicitly labelled as job/role searches; a generic site-wide search can replace the careers page with blog results. Rank posting detail URLs before team/location/language filter combinations, while retaining the same bounded coverage reporting. Saved recipes containing the older generic search selector require rediscovery.

Named developer/engineer/QA/analyst cards on a careers listing may use short same-host URLs such as `/react` or `/java`. Follow those links while preserving marketing/LinkedIn exclusions; a detail without a conventional job path still needs a role heading, substantive requirements/responsibilities and application instructions. Category buttons and JavaScript-only modals without links still require verified source-specific navigation; extra crawl time alone does not resolve them.

Collection corrections (2026-09-28): `navigation.ts` ranks verified ATS boards ahead of detail/localized pages and excludes marketing/student/blog navigation. Full public ATS feeds explicitly mark `completeListing` only when every record is complete; already supplied details are not fetched again. Separate explicit sources/listings remain in scope. Embedded board discovery resolves an otherwise empty widget shell without hiding unfinished pagination. `description-quality.ts` flags short or cookie-only extraction, retaining the body in audit; cookie-only descriptions cannot receive an eligible shared decision or spend an assessor call. Consent overlays are removed from readable text. CAPTCHA requires a visible challenge or an explicit challenge/access-denial heading, not a word in an article. Existing pending access reviews are never cleared by these code changes alone.

Repair uses an unvisited verified navigation alternative or retries discovery without failed saved controls, under the same source budget. When neither changes the approach, repair is skipped. `trace.repairOutcome` and Markdown reports distinguish `succeeded`, `failed` and `not_attempted`; prior recipes/evidence remain available. Extraction-version invalidation prevents silently reusing observations produced by the older detector.

## Persistence

`saveCollection(collection, write)` in `postgres.ts` writes raw/audit snapshots to `noco.collection_runs`, never canonical vacancies. Completed snapshots are immutable; an unclassified `running`/`interrupted` scan may advance under the same frozen configuration. `loadCollection` supports later classification/reporting without another crawl.

`saveClassification` validates global rules and selected populated stacks, then atomically promotes accepted roles with full descriptions to `noco.vacancies` and matching stack links to `noco.vacancy_stacks`. Market and explicit destinations persist in existing vacancy `sources` JSON and complete run/classification snapshots; no new table or migration is required. Rejected/review-only roles stay in audit. Existing history and source-binding checks remain intact.

URLs: `noco.vacancies.apply_url` is the actual HTTP(S) application target. Despite its name, `canonical_url` is a deduplication key and can contain `greenhouse:<id>`; it must not be opened in a browser. Original `Position.url` and `Position.applyUrl` are preserved in `collection_runs.collection.positions` and classified snapshots. The ATS adapter opens `Position.applyUrl`; `sources` JSON describes provenance rather than replacing those URLs. A future naming/storage cleanup should separate a consistently clickable posting URL from the canonical identity without breaking existing history keys.

CLI `collect --scope scope.json --run ID --out collected.json` remains the independent collection action. Standard scoped execution uses `scan --company-ids IDS --db-stacks IDS --run ID`. `--db-stacks`/`--students` narrow membership; company IDs narrow sources and coverage issues together. Unknown/inactive company IDs fail preflight. `--offline` fixture results cannot authorize live submissions.

`checkpoint.ts` stores configuration fingerprints, checksummed page documents/original fetch times, and the exact final snapshot under `storage/external-responses/collections/<run>/`. `--resume` reuses successful page reads only under unchanged scope/settings. Final snapshots are immutable and replayable after uncertain SQL commit acknowledgement. Pending gate reviews must be resolved before a new run; resuming a completed snapshot does not recheck access. Before removing any stale lock, verify its recorded process has exited.

## SQL source memory and replay

`scan --await-review` stops after saving the collected snapshot and validated source memory, with classification still null. Recipes and original search timestamps persist before the review handoff; unassessed findings are not promoted to vacancies. It prints the exact collection digest and rule hash. Review that saved text, then repeat the same command with `--resume --assessments FILE`; the existing evidence-checked review adapter classifies and finalizes SQL memory/reporting without reopening websites. Classification can add decisions to the same run's source memory without replacing its recipe or renewing search timestamps. A review is recorded as `human`/`assistant_session`, never as a paid API response. Completed classifications stay immutable. An old run already finalized as pending requires a new run using its fresh source snapshots.

`memory-postgres.ts` extends only `noco.sources`: nullable JSONB `collection_recipe`; non-null JSONB `collection_state` default `{}`; nullable TIMESTAMPTZ `last_search_attempt_at` and `last_complete_search_at`. Inspect with `scan-schema`; migrate explicitly using `scan-schema --apply --expect-checksum HASH` through the checked working DB wrapper. Runtime never auto-migrates. Reload/Meta Sync the existing PostgreSQL source to expose fields in NocoDB.

`recipe.ts` first replays verified listing URLs and recorded semantic public-listing controls. No scripts, coordinates, application actions or credentials are recipe inputs. It validates substantive descriptions, complete pagination and explicit empty states. A failed recipe permits one repair sharing the same page/time budget (default 24 reads, five minutes per source). Only successful validation replaces a recipe; the old recipe and repair actions stay in the SQL run audit. Original source URLs/identities/provenance remain unchanged. LinkedIn and excluded hosts are blocked on replay/repair/navigation; API redirects are not followed unchecked.

`source-memory.ts` defines the versioned recipe/state/trace contracts and seven-day freshness. A compatible latest complete snapshot younger than seven days can be reused without browser reads; reuse preserves search and posting timestamps. Partial scans never renew completeness, though inspected accepted roles remain usable. `--force-refresh` bypasses age reuse. Pending login/registration/robot/CAPTCHA reviews are paused even when forced, unless explicitly retried. The standard `scan` queue is SQL `collection_state.review`; independent legacy `collect` retains its existing local review adapter.

An existing `collection_state.operatorAvailability.status=unavailable` or `collection_state.health=unavailable` also pauses source execution before recipe replay. Only explicit `retryReview` retries it; the pause does not clear recipes, snapshots, decisions, timestamps or source identity.

Each run journals actions locally before continuing and saves completed traces into `collection_runs.collection.audit[].trace`: URL, operation/outcome, duration, recipe revision, replay/repair history and observation references. SQL records an actual search attempt at its start; final memory/cache updates are one transaction per completed campaign, one update per source. Optimistic state comparison prevents overwriting concurrent changes. Interrupted runs are saved as interrupted, not complete. Resume requires the original scope/configuration and reuses original checkpoint observations; partial completed SQL commits are reconciled by run ID.

For a single complete public ATS response, ETag/Last-Modified validators are retained beside its saved source snapshot. A conditional HTTP 304 reuses that exact saved body; a 304 without the corresponding validated snapshot is rejected. Paginated HTML shells are never treated as proof that their detail pages are unchanged; those pages are fetched and semantic content hashes compared. Login/robot/read failures capture a screenshot when the browser permits it, with an evidence reference in the same action stream; screenshots are not required to complete an ordinary successful read.

`collection_state.snapshot` references the latest source audit directly; decisions contain exact input hashes, evidence and original reviewer/API provenance. Full bodies remain in existing run/vacancy storage. No historical-run sweep is needed. When a previously seen posting disappears from a complete listing, the workflow checks its official URL within the remaining budget. Only explicit closed text or HTTP 404/410 marks that URL closed; failed/partial scans and listing absence alone never do. Vacancy/application history is retained. Distributed source claims and automatic scheduling remain deferred.

`posting-content.ts` strictly validates publication dates (including impossible dates), anchors relative day labels to their original observation date and never treats update/crawl timestamps as publication. `publication-date-precheck.ts` reads its threshold and reasons from the vacancy-selection skill. A reliable expired listing row is omitted before its detail read; invalid/future/contradictory/ambiguous evidence is inspected and remains review-only. Source audit retains URL, evidence, reason and UTC as-of date. The same verdict is reapplied after extraction, on weekly reuse and before accepted-only SQL persistence.

Codex investigation handoffs serialize at most 32 KiB initially and 64 KiB on the single expansion. Focused observations carry exact hashes and local checkpoint references for full evidence; oversized packets become explicit pending work.
