# Sequential application workflow

For browser work, use `application-status --input FILE --worker-packet [--position ID]`: one target's small deterministic handoff, with complete details referenced on demand. This starts no AI worker and changes no usage allowance. An authorized fresh worker can reuse the same owned browser process; its paused `status` command reads the last in-memory checkpoint without a resume/submission. See the runbook for exact scope and safety gates.

Start/resume procedure: [RUNBOOK.md](RUNBOOK.md). `application-status --input workflow.json` reads a compact SQL checkpoint without a browser or AI, including exact allowed options for unresolved fields. Application commands print a compact batch summary by default; `--verbose` restores full stdout detail. Complete reports and evidence remain on disk/SQL. Resumed compatible batches skip the preliminary dry preparation pass; the live stage still inspects the form, reuses per-field answer checkpoints, verifies the exact attachment and rechecks eligibility. Unknown attempts only reconcile. Explicit `humanAssistance[positionId] = { observedAt, reference }` records observed help without authorizing another attempt.

`run-application --input workflow.json --live|--dry-run [--resume] [--close]` composes SQL eligibility, Dolphin/Patchright form preparation, per-vacancy tailoring, upload, submission and reporting. `prepare-application` stops after form inspection; `tailor --live` consumes an already prepared batch without opening a browser. Existing independent stage interfaces remain available.

Use `prepare --workflow workflow.json --dry-run`, `tailor --input workflow.json --live`, then `apply --workflow workflow.json --live --resume` to call those stages independently. The apply stage cannot generate a CV. Standalone tailoring persists the returned artifact in the SQL batch before reporting it. A failed semantic test review is retained with its PDF; resume must neither regenerate nor upload it.

Input contains `candidateId`, `studentId`, `stackId`, `collectionRunId`, immutable `positionIds`, `batchId`, and an approved `tailoringPolicy` (`id`, `approvedAt`, `approvalReference`). Default applications use a tailored PDF. Explicit `cvMode: "original"` with `originalCvApproval: { approvedAt, approvalReference }` uses the unchanged original PDF without a tailoring call or API key. The selected original path/hash and approval persist in the existing batch before upload; an attempted tailored attachment cannot be switched. The profile and market come from current SQL relationships. No Drive fetching or new business tables. The current shared selection hash, collected student membership, current market/stack, original restrictions and history all remain gates. Contextual restriction reviews bind the complete rule, confirmed student facts and vacancy description with `inputHash`; changed inputs require a new review.

Normal preparation sends the original PDF plus the complete saved vacancy description to the shared tailoring service. Generation intent is journaled before the single POST. Original/result hashes and the description bind a separate artifact; input changes cannot reuse it, and a lost result cannot authorize another POST. `application-status` reads only selected, binding-verified local journals: a consumed request without a result reports `resolve_tailoring_failure`, while a saved result reports `recover_tailoring_result`. Future transport failures record only sanitized error code, HTTP status and time. Resume may download the saved result URL again. Production validation is local PDF structure/readability and binding; it does not require semantic or visual review.

Optional `campaign` data explicitly authorizes temporary test answers, initial target identities and at most three five-company follow-up batches. `testAnswers` contain exact `campaignId/studentId/batchId/positionId` scope plus reviewed values/evidence. These never enter candidate facts or global skills. `testReviews` bind assistant review to the exact output SHA-256; this review gate applies only when a test campaign is supplied. All page rendering, semantic comparisons and before/after commentary are test work, not a production AI stage.

`campaign.ts` persists immutable scope and progression. Initial captured success and a passed CV test unlock follow-up collection. A new explicit operator instruction to abandon the initial target may instead be recorded as `initialContinuation`, bound to its batch with dated approval evidence; `initialConfirmed` and the original outcome remain unchanged. This allows only the already authorized follow-up company scope. Finish the first batch containing actionable targets; failures do not create replacements. Collect all populated selected stacks, not only the tested student. Three empty-for-student batches terminate the campaign; notify-only/Telegram/access reviews remain reported separately.

`openCampaign` uses the initial SQL application's `campaignProgress` as authoritative state and mirrors it locally. After a complete scan and current student/restriction matching, call `recordCampaignCollection` with the complete actionable target list, exact company IDs and all selected stack IDs, then save. This freezes the collection run and application batch together. The normal scan command must receive `--concurrency 1` for this campaign. Assistant classification/answer/review inputs remain explicit checkpoints; this is not an unattended AI agent loop.

The shared Dolphin integration owns authentication, proxy reads and start/stop. Its filesystem ownership guard coordinates this host's HH/external lifecycles. Never remove a lease without reconciling its recorded owner, never stop another owner, and never use busy-profile cleanup for an external session. CDP attachment selects Patchright explicitly. LinkedIn is blocked. Handoff tabs stay open until resume/exit while the command remains interactive.

A busy profile is a deferred scheduling outcome, not a pipeline/application error. The command returns normally, writes `availability.json` and `availability.md`, leaves existing application evidence intact, and creates no failed application. Continue other students sequentially; later resume the same frozen targets. Busy cloud tags/status and ownership/start races must not attach, stop, or clear the other session.

Outcomes and selected artifact references persist through the existing PostgreSQL batch/application transaction. Reports contain links to exact PDFs and distinguish technical checks, test review, operator assumptions and captured confirmations. Events are sanitized; no tailoring key or signed download URL belongs in manager output. Logs cannot trigger external retries.

Tests: `application-workflow.test.ts`, `tailoring.test.ts`, `dolphin-browser.test.ts`, existing ATS fixtures, shared Dolphin runtime tests and web-console tailoring transport tests.
