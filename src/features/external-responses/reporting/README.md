# Reporting

Collection reports separate accepted, excluded, substantive/data-review and unassessed vacancies. A consumed/cached `review` decision is not an outstanding model request and is never described as application-ready. Both total title-rejection observations and distinct rejected URLs are shown; repeated company/ATS sources cannot be presented as distinct vacancies. Session-classification usage consumes final saved response snapshots, deduplicates response/batch IDs, preserves partial/unknown measurements and leaves coordinator usage unknown. `classification-usage.json` totals saved batches, including resumed results; it does not imply all usage occurred in the latest invocation.

Application reports link the exact `PreparedCv` file with original/result SHA-256 and technical/test-review provenance. Test campaign answer assumptions are labeled and never presented as confirmed facts. The sequential workflow writes one report, events stream and existing JSON/CSV/failure exports per batch. Deep CV review belongs only to tests; ordinary PDF validation is not described as a semantic review.

Standard `scan` produces one Markdown report under `logs/external-responses/scans/<run>/report.md` plus one `events.jsonl` diagnostic stream. It includes frozen company coverage, accepted roles/stacks, pending work, access reviews, recipe repair/replay, cache hits and original assessment provenance. Page-read counts are reader operations, not browser asset HTTP requests. API requests/tokens are measured by the existing recorder in that same stream; unavailable token counts are unknown, never invented. Internal recovery checkpoints remain under storage; full descriptions are not repeated in the default report.

Use `scan --export` only when detailed classified JSON and company/vacancy CSVs are needed. `scan-report --runs A,B,C --out comparison.md` generates one saved-SQL comparison without a browser or AI. The older standalone commands below preserve their output contracts and historical files.

Codex-engine reports additionally identify investigation status, proposal count, engine/recipe binding and active source time. Every selected company appears in the company coverage table, including companies with no supported source. A company counts complete only when all selected sources are complete and there is no source-coverage issue. Diagnostic inspections count against reader budgets. Session tokens/cost remain unavailable; zero paid API calls is never described as zero AI usage.

Implemented AI usage reports: CLI AI calls produce requests.jsonl, summary.json, summary.md and operations.csv under logs/external-responses/ai-usage/<invocation-uuid>/. They distinguish logical calls, retry HTTP attempts, known input/output/cached-input tokens, unknown usage and exact repeated inputs; operations are sorted by known total tokens. No private prompt/CV content is stored. External tailoring tokens remain unknown and its separate web-console endpoint is not metered here. See [measurement scope](../MVP_REUSE_PLAN.md#usage-measurement-implemented-now).

`generateReport({candidateId,batchId?,discovery?},{store})` reads saved candidate/history/batches and returns Markdown, CSV, JSON results, totals, failures and robot rejections. `generateCollectionReport(classifiedCollection)` returns source coverage, stack counts and blockers. Neither requires browser or AI. Normal CLI reports read SQL; `--offline` reads saved file snapshots with no database connection. CLI writes returned artifacts locally.

Count only explicit captured receipts as confirmed automated results. Label operator-reported confirmation and manual assistance separately. Keep uncertain outcomes and historical failed attempts visible. Redact secrets and exclude detailed candidate answers from manager exports. Database campaign reports show membership counts, not lists of student IDs. Detailed restriction decisions remain in saved application positions for debugging.

CLI: `report --candidate ID --student DB_ID --batch ID` (SQL), or add `--offline` for saved file state; `report-collection --input classified.json --out DIRECTORY`. Tests: totals/redaction/history cases in `contracts.test.ts`, saved-artifact reporting in `pipeline-cli.test.ts`. No automatic manager/student messages are sent by this stage.

Collection reports include source coverage failures, deferred adapters and a report-only company section. SQL application outcomes distinguish captured from candidate-reported confirmation; imported unverified legacy history is never counted as a new success.

Collection summaries distinguish unique discoveries (audit observations) from accepted vacancies (the union of matched stack IDs). Only the latter enter the canonical vacancy directory. Per-stack excluded/review counts remain diagnostic; a multi-stack role counts once in the accepted total. Source-table/CSV counts are labelled Discoveries, not accepted SQL rows.

Updated 2026-09-28: company totals use canonical company IDs (exact names for file-only manifests), independently of URL counts. `generateCollectionReport` returns `gaps` separately from structural `blockers`, plus accepted `vacancies` and `vacancyCsv`. CLI writes `accepted-vacancies.json` (complete text, decisions, routes) and `.csv`. Markdown lists each posting, stacks, description-language market and next action. Higher titles flag the required student exception; reviewed classifications identify their `assistant_session|human` origin and cannot be described as unattended API success. `Vacancies with Telegram — apply later` is normal deferred work. Source-access reviews have a separate section. Report-only companies stay report-only even when a Telegram recipient exists.
