# Applications

The [resume runbook](../application_workflow/RUNBOOK.md) is the operator entry point. `source-memory.ts` stores only verified public form schemas in `noco.sources.collection_state.applicationForms`, scoped by source/company/origin/engine/signature. Private answer checkpoints remain in the existing SQL batch. Memory writes are diagnostic: their failure cannot cause another submit. The shared source collection recipe is never replaced by application form memory.

Efficiency TODO: [changed-application persistence](../EFFICIENCY_PLAN.md#sql-and-persistence-implications) replaces growing full-batch rewrites through a versioned adapter. Current saveBatch behavior below remains until that contract and its recovery tests are implemented.

Public entry: `applyToPositions(input,{store,adapters,answers,restrictions,verification?})` in [index.ts](index.ts). `execute.ts` is the internal ATS lifecycle, not a campaign entry point. Input binds a candidate, complete classified collection, stack, explicit targets, batch ID, limit and dry/live mode. Returns durable `BatchState`.

Live mode requires a database campaign and its student binding. Selected roles must match the stack and preserve the collected company/title/description/location/URLs. Student eligibility is recomputed from current restrictions before opening, uploading and submitting; a saved fit or `reviewOverride` cannot bypass it. Missing/ambiguous restrictions block the attempt with evidence. Unknown prior submissions are reconciled, never submitted again merely because eligibility changed.

Each restriction check receives the [student eligibility context](../candidate_matching/student-context.ts): identity and explicitly confirmed facts, with CV-derived facts and CV references excluded. The full candidate remains available only to preparation; changing the original CV alone cannot change eligibility. `preparedCvs` supplies per-position artifacts and `requireTailoredCv` forbids original fallback by default in the sequential workflow. Its explicit `cvMode: original` requires dated approval, binds the exact original path/hash to the batch before upload, and cannot replace an attempted tailored attachment. Artifact or original-file hashes are verified immediately before upload; candidate facts/original CV stay unchanged. Legacy callers remain compatible when the gate is not requested.

Only explicit authorized live mode uploads/submits. Dry run inspects forms and prepares answers. A candidate lock and durable submission intent prevent concurrent/uncertain repeats. Targets, student binding, collection and limit remain immutable across resume. Failures do not authorize replacements. Success requires captured confirmation evidence.

Uncertain submissions never retry automatically. A new explicit operator request may supply `retryAuthorizations` bound to the candidate, batch, vacancy and exact prior attempt number, with dated approval evidence. Reconciliation still runs first and a captured receipt cancels the retry. One approval permits only the next attempt; earlier uncertainty and authorization remain in the audit. Eligibility, attachment verification and duplicate protection still apply.

Each live Submit click starts a minimal `evidence/<position>-request-<time>.jsonl` trace before the click. It records timestamps and counts for possible application writes and their network completion, without request bodies, response bodies, URLs, cookies or tokens. The page-owned listener and trace remain active across CAPTCHA handoff and adapter reopen in the same live process; each reconciliation adds an `observation_complete` checkpoint. Only a new explicit attempt starts a new trace. A missing or incomplete trace, including an empty response list, cannot prove that no write occurred and never authorizes a retry; reconcile against an employer receipt and SQL attempt history first. A trace write failure before Submit blocks the click; a failure after it leaves an uncertain outcome. This change cannot recover network events lost in an earlier process.

Application adapters: Ashby, Greenhouse, Lever, Recruitee, BambooHR, SumUp, and Gurtam. SumUp resolves only the Greenhouse application iframe observed on the matching official posting; the temporary `validityToken` stays in browser navigation and is removed from inspection and outcome URLs. Gurtam uses its native `#recruitment-applications-form`, visible custom selectors with backing-value readback, the selected PDF and filename acknowledgement, and both required consent controls. Its pre-rendered hidden confirmation is never a receipt; success requires the visible submitted state, while response validation errors override a visible success message. Both company engines reuse the existing answer, verification, durable intent, request trace, and outcome pipeline. Unsupported forms and verification gates create handoffs. Preserve missing-answer, CAPTCHA, robot, validation and unknown-outcome distinctions. Diagnostics cannot cause submission retries.

`captcha.ts` detects visible standard hCaptcha challenge and reCAPTCHA puzzle frames during inspection and outcome observation. Hidden widgets and unchanged checkbox/background frames are not proof of an active puzzle. After Submit, `ats-forms.ts` also compares provider frames with their pre-submit baseline: a newly visible or expanded opaque challenge creates a verification handoff even when its body text is inaccessible. The same live tab may continue its original submission only after a provider checkbox reports verified, the challenge is gone, no application write was sent, and the workflow's before-submit callback rechecks eligibility, fields and durable intent. A disappearing puzzle alone remains uncertain. This is detection, not a solver: no third-party solver receives candidate data or verification tokens. Only an actual employer receipt earns captured confirmation; ordinary reconciliation does not assert human assistance.

`verification-controller.ts` receives the already-owned ATS `Page` while its workflow process remains paused. It can inspect a visible hCaptcha frame, save a cropped 60-second snapshot, and make one click/drag inside the same frame after URL, frame identity, decoded-pixel hash and bounds still match. DOM snapshots also require readable puzzle text; an opaque frame instead requires explicit review of a `capture-visual` image before an action. It never clicks Submit. `verification-solver.ts` implements the optional documented 2Captcha DragAndDropTask transport with one durable create intent and a 45-second polling deadline. It requires explicit scoped workflow enablement and `TWO_CAPTCHA_API_KEY`; only verified provider-DOM background and movable-piece images can be sent. The current runtime asset extractor returns unsupported for opaque live challenges, so a key alone does not enable automatic solving. No candidate/CV/form data or full-page screenshot is sent to the provider. Tests: `verification-controller-browser.test.ts`, `verification-solver.test.ts`.

Lever's structured current-location field uses the reviewed full city/country query, then requires a unique matching suggestion and verifies the hidden `selectedLocation` value. Typed visible text alone is not a saved location; ambiguous suggestions block submission. An explicitly blank optional field is cleared and verified empty without waiting for suggestions; a required location cannot use this path. Its question labels come from `.application-label`, excluding hidden autocomplete/status text.

BambooHR support is limited to an employer subdomain's `/careers/{numeric job ID}` page. It opens the visible application from that listing and inspects the applicant form, including the required resume upload and Fabric Country selector with backing-select readback. It uses the shared field inspection, attachment verification, submission intent, request trace and receipt classifier; it never invents an `/apply` endpoint. Missing required candidate facts remain input handoffs.

Tests: `contracts.test.ts` exercises internal lifecycle; `student-eligibility.test.ts` and `pipeline.test.ts` exercise the public gate; `browser.test.ts` contains intercepted ATS fixtures. `ats-continuation-browser.test.ts` covers verified continuation, automatic receipts, repeated/disappearing puzzles, network loss and one-click bounds even without a network write. Run `npm run external:responses:test`; use `EXTERNAL_RESPONSES_TEST_DRIVER=patchright` and optional explicit `EXTERNAL_RESPONSES_TEST_CHANNEL=chrome`. No live employers are contacted by tests.

## PostgreSQL state

Normal CLI execution uses `createPostgresStore`: candidate facts/CV remain local; SQL stores immutable batch identity, per-student locks, intent and application outcomes. Locks are keyed by database student ID, so different local aliases cannot run concurrently. Outcome projection and the batch checkpoint commit in one transaction. A local export failure cannot undo a durable intent. Historical file batches remain duplicate evidence; an old file-only batch cannot silently resume as a new SQL batch. `--collection-run ID` loads a saved classification. Database student binding and collected company/source IDs are required. Tests: `postgres-pipeline.test.ts`.
