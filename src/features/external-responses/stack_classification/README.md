## Constrained session classification (2026-09-30)

Whitespace comparison also recognizes literal HTML nonbreaking-space encodings (`&nbsp;`, `&#160;`, `&#xa0;`) left in captured text. It returns the original contiguous source span including the entity; it does not decode arbitrary entities or normalize words, case, numbers or punctuation. Previously bound pending responses can use the existing recovery command without a new generation.

Evidence comparisons accept whitespace differences only (including non-breaking spaces and line wraps), then retain the exact original contiguous source span. Words, case, punctuation and numbers are not normalized. Raw responses remain unchanged in diagnostics. Pending `assessment_evidence_invalid` responses may be deterministically revalidated under their unchanged batch/input/policy binding; this never regenerates an answer or retries a provider failure.

Recover a finalized run with `classify --collection-run OLD --run NEW --db-stacks 2,3,5,7 --recover-session-results logs/external-responses/scans/OLD/session-classification --classification-session-policy POLICY --out FILE`. It checks current rules and stack descriptions, reuses saved responses only, applies current deterministic gates, creates a separate immutable SQL audit, and uses accepted-only vacancy persistence. Original search timestamps and raw failure evidence survive. Source decision caches are updated without renewing search freshness. Missing responses remain blocked; this command cannot call AI or crawl.

`assessment-batches.ts` packs full descriptions and candidate stack requirements into bounded JSON requests. Rules/stack descriptions occur once per batch; output schema bytes count toward the 64/128 KiB envelope. Descriptions are never shortened. Oversized cases remain pending. `assessment-handoff.ts` now emits `batches.json` alongside the existing independently consumable packets.

`classification-runner.ts` consumes an injected transport and persistence contract. It requires verified tool exclusion and structured output before generation. It admits one request at a time, writes durable intent before dispatch, validates exact batch/position/input hashes, stack scope and literal evidence, and saves the result. Missing/duplicate rows, invented evidence, global/stack contradictions and reported tool calls are invalid. Invalid, interrupted or uncertain generation never automatically retries. A transport must honor the passed abort signal and enforce the policy's output-token limit; these are required live adapter acceptance checks, not prompt instructions.

`session-classification.ts` composes current prechecks, exact cache lookup, batches and the existing classifier. `scan --classification-session-policy FILE --budget-campaign DIR --concurrency 1 --classification cached` uses it, without interleaving applications or changing engine development. A whole-run local lock prevents separate invocations dispatching different batches simultaneously. Local `.intent.json` and atomic `.result.json` records preserve uncertain outcomes; changing policy/input bindings cannot reuse a result. `maxBatches` includes the frozen batch slots consumed before resume, including failed requests. The existing account-wide budget remains shared and cannot be reset by this flag.

**Codex transport:** `codex-classification.ts` replaces the former unavailable stub. Before dispatch it uses the installed App Server and the native OpenAI provider against a loopback mock endpoint, with both documented base URLs redirected locally. A synthetic canary verifies that the outbound request has no tools, selects Sol and carries JSON schema; the endpoint returns an error without inference. Headers/credentials and request bodies are not logged. Failed checks prevent dispatch. Runtime uses the same per-thread feature overrides, a fresh ephemeral context, no repository/skill catalog instructions, read-only permissions and no fallback. The adapter requires a ChatGPT account, refusing API-key accounts. Engine workers and user-wide configuration are unchanged. The probe is repeated by each transport instance, so changed local capabilities cannot silently reuse a previous proof.

Cancellation targets only the adapter's owned turn; early completion/cancellation races, malformed JSON, unexpected tool events and a 180-second deadline are handled. Failed responses retain their measured usage and durable intent; resume never regenerates them. Windows shutdown closes the owned pipes so inherited handles cannot leave the workflow hanging. `classification_transport_preflight` records the sanitized wire-check counters in the run's diagnostic stream. The offline probe validates serialization/capabilities, not live model quality or successful provider inference.

**Limit semantics:** App Server does not expose a provider-side maximum output-token field. Policies must explicitly set `outputLimitMode: "observed"`: the adapter cancels when reported output usage exceeds the configured threshold and also bounds received output bytes. Delayed usage can overshoot, including reasoning before the first update. This is not a hard provider cap. Zero retries means no adapter turn redispatch; native Codex transport reconnection/retry behavior is not a separately configurable guarantee here. Weekly admission/stop monitoring remains mandatory, and this implementation does not reset a stopped budget or approve a new one.

Session policy v1 explicitly binds Sol/medium, prompt hash, 64/128 KiB input bounds, observed output-token limit/mode, batch limit, zero adapter retries, no tools, approval fields and checksum. Proposed policies with blank approval fields are invalid. Only validated decisions get assessment provenance; capability rejection produces none. `classification-usage.json` includes successful and failed response snapshots deduplicated by response/batch identity, not summed notification updates; unknown/partial usage stays explicit. These are saved batch totals across resume, not necessarily new usage in that invocation.

Tests: `classifier-batches.test.ts`, `classifier-workflow.test.ts`, existing engine, SQL, cache and quota suites. Six captured public descriptions and twelve declared boundary cases support future comparison using `benchmark/compare.ts`; passing mock contracts does not establish model accuracy or live token savings.

Before semantic assessment, the title policy intersects each title's routes with the selected populated SQL stacks. An empty intersection is a deterministic exclusion, never pending AI work. Combined assessments and session packets contain only that posting's candidate stacks. Noncandidate stack decisions are filled as deterministic exclusions; generic software/backend titles may retain several candidates. Global description, geography, salary, age and workload rules still apply. A title match alone cannot authorize a SQL vacancy save. Routes are always recomputed from current rules/scope, so stale audit metadata cannot bypass these gates.

Global vacancy rules run first, without a student or CV. Only global passes reach stack matching; only roles matching at least one selected populated stack can enter the canonical vacancy table.

`precheck.ts` applies the skill's deterministic role-family/title, date, salary, geography and description-quality rules
before semantic assessment, including saved observations. Review packets use the same
gate. Obvious exclusions require no AI or human review; unresolved engineering roles
proceed automatically to the configured assessor. Missing descriptions remain explicit
extraction work. Deterministic outcomes are not recorded as model assessments.

Role recognition is a closed allowlist, not stack acceptance. Development, DevOps/SRE,
testing and project/product-management families are recognized; forward-deployed and
AI product engineering require body verification. Other posting titles are rejected.
QA/testing still cannot enter Java/Python development stacks. No new stacks are created.

`salary-precheck.ts` parses explicit salary clauses or structured compensation and calls
the existing `monthlyUsd` arithmetic. It checks the upper bound against the floor in
`salary-precheck-json` in the skill; minimum-only offers are not ceilings. Missing salary
is not a rejection. Ambiguous amounts/currency/periods, net pay, missing working hours or
FX become deterministic data-review outcomes without an AI call. Bare `$` is ambiguous;
USD/US$, EUR/€, GBP/£ and explicit supported currency codes are recognized.
`classify --exchange-rates rates.json` and `scan --exchange-rates rates.json` accept `{asOf,source,usdPerUnit}`. Rates are frozen
in the result and decision key, not fetched or guessed by AI. API callers can inject the
same `exchangeRates` object. Review packets accept the same option and freeze it in their
manifest. The cache-aware path runs these gates before cache lookup or model dispatch.

`geography-precheck.ts` reads `geography-precheck-json` from the same skill. It recognizes exact country/region fields, terminal country codes after cities, explicit employee residence requirements and worldwide remote alternatives. CLDR supplies country names; allowed countries/regions stay in the skill. Headquarters, travel and time zones are not employee restrictions. Conflicting requirements, negation, unknown places and generic Remote labels proceed to semantic assessment. Only confident outside-area constraints exclude automatically. Allowed geography never skips global/stack assessment. Stored student geography exceptions remain outside this shared default pool.

## Where to edit selection rules

**Edit [vacancy-selection/SKILL.md](../../../../.agents/skills/vacancy-selection/SKILL.md), under `Rules`, using ordinary prose/bullets.** The CLI reads that file automatically. It is the single authoring location for shared vacancy rules; no global-rule SQL columns or second rules list are needed. The job-hunting skill links to it too.

### Global vacancy rules

[rules.ts](rules.ts) reads the file once per classification and snapshots its active text, source path and SHA-256. YAML frontmatter and HTML comments are excluded. Missing/empty files fail explicitly. Author semantic eligibility under the existing `## Rules` heading (until the next level-two heading). `semanticRules()` sends that complete section to the session classifier; executable precheck configuration and unrelated workflow prose stay out of its input. Legacy/custom files without that heading retain their entire text. No second rule file is introduced.

[combined-ai.ts](combined-ai.ts) is the normal SQL-campaign assessor: one request contains the full shared rules, complete posting and all selected stack descriptions; it returns distinct global/per-stack decisions with literal evidence. Global exclusion/review prevents canonical insertion. A global pass still needs a stack match. The older `global-ai.ts`/`ai.ts` adapters remain available to independent callers/fixtures; the SQL CLI no longer chains their calls. No configured assessor means explicitly pending decisions, never a silent pass or “no suitable vacancies”.

The complete file hash remains audit/review binding. `decisionRulesHash()` covers the semantic section plus canonical executable precheck configuration. Matching/preparation/application gates compare that business-policy hash: real policy changes still require current classification; unrelated documentation edits do not. An in-progress run retains its exact frozen configuration. Use `--selection-rules PATH` consistently for explicitly selected alternate files.

## Interface and persistence

`classifyVacancies({collection,stacks?,selectionRules?},{assessGlobal?,assess?})` in [index.ts](index.ts) returns `ClassifiedCollection`: the frozen rules, one global decision per discovered position, per-stack matched/review/excluded IDs, evidence, configuration issues, readiness and a digest. It does no file/browser/SQL I/O; injected assessors may call AI. Load the Markdown in composition with `loadSelectionRules()`. Historical/unscoped fixtures may omit it, but SQL promotion rejects classifications without a rule snapshot.

Database campaigns derive stacks from `collection.scope`; overriding them is forbidden. The combined result is passed through existing global/stack integrity guards. The structured-policy assessor remains available for offline profiles. Neither stack labels nor a vacancy create new DB stacks.

Missing descriptions receive review without any assessor call. A role may match several selected stacks but still creates one vacancy row. All-excluded and review-only discoveries remain in audit/checkpoints.

`assertClassificationIntegrity` checks digests, global-decision coverage, DB stack scope and decision/group consistency. A global rejection/review cannot coexist with an accepted stack decision. `assertCollectionReady` requires exactly one valid terminal outcome for every source. Partial/unavailable sources and unsupported-source registry gaps remain reportable; they do not veto complete accepted vacancies. Missing/ambiguous audits (`terminal: false`) still block the application stage. SQL promotion remains accepted-only.

`saveClassification(value,write)` in [postgres.ts](postgres.ts) requires an existing saved collection, validates global/stack decisions, then atomically upserts accepted full descriptions into `noco.vacancies`, matched links into `noco.vacancy_stacks` and the classification audit into `noco.collection_runs`. Workflow table placement requires migration 006. No raw vacancy insertion path exists. Later rejected observations cannot overwrite earlier accepted/application history. Rules live in the file; SQL stores the run's rule snapshot/evidence in existing JSON, with no migration.

CLI: `classify --collection-run ID --out classified.json` or `classify --input collected.json --out classified.json`. `--no-ai` leaves global rules for review. `--stacks java|catalog.json` is for unscoped offline fixtures. `report-collection` exports `selection-decisions.json` and includes rule hash/global totals in Markdown.

After editing stack descriptions, create a fresh scope; existing scopes retain old descriptions. Changed rules/stacks require a new run. A fresh compatible source body can be reused while its decision is invalidated and reassessed or left pending.

## Exact reuse and paid-call activation

`refreshSavedClassification` and CLI `classify --refresh-saved --collection-run OLD --run NEW --db-stacks IDS` revalidate saved descriptions without crawling or AI calls. SQL writes go through the existing accepted-only persistence guard in a new run. Supported deterministic prechecks are recomputed; semantic reuse requires identical prose and stack policy plus proven `semantic-v1` provenance. Changed prose/stack policy and legacy decisions stay pending for explicit review. Original observation timestamps and run history remain unchanged. Source cache management remains part of `scan`. See [RUNBOOK.md](../application_workflow/RUNBOOK.md).

`classifyWithReuse({collection,rules,cache,policy},{assess?,onDecision?,now?})` in `reuse.ts` has no storage/browser dependencies. It returns the composed snapshot plus semantic cache updates. Valid cache hits make zero assessor calls. Accepted, excluded and evidence-backed review assessments are reusable; transport/invalid-response/missing-assessor failures are pending and never cached. Original `api`, `human` or `assistant_session` origin and reviewed timestamp survive reuse.

`scan` loads current per-source entries directly from `collection_state.decisions`, referencing full bodies in the existing run/vacancy storage. `--seed-run ID` can import exact-input explicitly reviewed decisions; mismatches remain pending. It never labels session reviews as API output. Independent `classify` uses the same combined assessor contract; source cache management belongs to `scan`.

Decision key format 7 is `semantic-v1`: exact title/body, non-date metadata, semantic rules plus canonical precheck configuration, stack requirements, extractor, assessment policy and supplied dated exchange rates invalidate reuse. Publication evidence and the advancing UTC day do not enter that key. Older key versions are misses; rollout can require a one-time reassessment. Explicit reviewed seeding still requires exact historical rule/stack snapshots and is never an automatic rekey. Cached values store the semantic assessment; deterministic title/date/salary/geography eligibility is composed before reuse and persistence. No fuzzy similarity or student CV enters this decision.

Semantic geography uncertainty reaches the existing combined assessor rather than becoming a permanently blocked precheck. `geography-assessment.ts` requires any accepted decision to quote the unresolved location constraints from the posting; the same check runs on reuse and SQL integrity validation. Definite outside-area restrictions remain exclusions. Missing descriptions, invalid dates and unresolved salary arithmetic remain data-review work, not invitations to invent facts. Generic “authorized to work in the country in which they apply” adds no country restriction; explicit restrictions in the same clause still apply. Research publication requirements are not posting-date labels.

For explicitly authorized session review, `scan --await-review` saves collection and pauses. `scan --resume --assessments FILE` uses the existing exact collection/rule-hash review contract, saves its provenance, updates the source decision cache and generates the normal report. This is assisted semantic classification, not unattended deterministic classification. No student/CV enters the review.

Paid API execution defaults OFF. Activation requires `--classification api --inference-policy FILE`, `OPENAI_EXTERNAL_RESPONSES_API_KEY`, and `OPENAI_EXTERNAL_RESPONSES_MODEL` matching the approved model. The policy uses `cacheVersion:"semantic-v1"`; prior `exact-v1` approvals are intentionally invalid. No default approval, model or budget is generated.

`session-packet.ts` creates a full-description task containing the semantic Rules section and routed candidate stacks. `assessment-batches.ts` then shares these requirements within bounded batches. The serialized cap is 64 KiB initially and 128 KiB on the single expansion. Requirements and descriptions are never truncated; over-limit work is explicitly pending. The existing separately approved paid-API adapter keeps its original prompt/approval contract; this change does not activate or silently change it.

When `--exchange-rates FILE` is supplied, both session batches and saved assessment handoffs include applicable dated rate provenance and deterministic salary results. Arithmetic stays in code. Session packet protocol `session-batch-v2` supersedes the earlier rate-dependent v1/fx-v2 keys: protocol identity is stable across FX availability, and rate dependencies belong to each posting. This is a one-time compatibility boundary; historical decisions retain their old provenance. The classifier workflow fixture verifies outgoing evidence, acceptance and zero-dispatch reuse even after an FX outage for a role without stated pay.

Standard `scan` now obtains dated public ECB rates automatically through `infrastructure/exchange-rates.ts`, once per UTC day across serialized scans. Each run freezes its available/unavailable result for resume; an explicit `--exchange-rates FILE` still overrides automation. Historical resumes without a snapshot retain their old contract. Maximum response 64 KiB, timeout 10 seconds, no redirects or automatic retries, rates at most seven days old to allow non-publishing days. Unavailable feeds are reported and cached for the day to prevent retry storms; missing currencies and ambiguous/net pay still require data review. A stale frozen rate requires a new run, never silent replacement. Independent `classify` remains explicit-input only.

Only the currency actually used for a posting's conversion is included in its semantic packet/cache key. No stated pay or USD pay is independent of daily FX changes; a changed rate/date invalidates converted-salary decisions, and unrelated currency changes do not. No paid AI is used to fetch rates or perform arithmetic. Tests: `exchange-rates.test.ts`, `salary-precheck.test.ts`, `classifier-workflow.test.ts`.

The adapter sends complete substantive inputs or records a pending budget failure; it never silently truncates. Bounds apply to the full HTTP payload too. Duplicate automatic HTTP retries are denied before network transmission. Missing configuration leaves crawling and valid cache reuse available; invalid supplied policy fails preflight. No paid calls are needed for contract/browser verification. API usage records distinguish measured provider tokens from unknown usage. External CV tailoring is outside this stage and reports no known token usage.
