# Connection Inviter

Отдельная ручная операция консоли: [отзыв приглашений старше 14 дней](../invitation-withdrawal/ARCHITECTURE.md).
Она читает все ожидающие отправки из Unipile, не только нашу историю.
Использует тот же writer и блокировку аккаунта; правила отправки и квоты не меняет.

## Бизнес-цель

Администратор вручную запускает норму LinkedIn-приглашений без сообщения. Норма зависит от числа
connections и делится строго на 70% recruiters и 30% technical без замещения аудитории.
OpenAI и расписание не используются.

Дневная норма и обе audience-квоты замораживаются после первой успешной проверки аккаунта.
Если Unipile не вернул число контактов в профиле владельца, читается полный список
его контактов по 100 записей на страницу. Подписчики не используются для расчёта нормы;
неполный список не разрешает отправку. Интервал запросов Inviter — не менее 6,5 секунды.
Без выбранного stack безопасный режим выполняет только recruiter-часть и завершается как `partial`;
после выбора stack повторный запуск в тот же день добирает только сохранённый technical-остаток.

Live writer включается только через:

- `LINKEDIN_CONNECTION_WRITER_ENABLED=true`;
- `LINKEDIN_CONNECTION_WRITER_ID=<stable-id>`.

## Поиск и отправка

Каталог содержит столицы и крупные IT-хабы. Сначала по `runId` стабильно перемешиваются крупные
рынки найма, затем резервные города. Ранее использованные города идут в конце своего уровня.

Для каждого города независимо перебираются простые Unipile V2 `keywords`:

- recruiter: Recruiter, Talent Acquisition, Sourcer, HRBP, Human Resources и People-функции;
- technical: aliases stack с Developer, Engineer, Backend Developer, Software Engineer и Tech Lead;
  для GO сначала используется `Golang`, затем `Go`.

В запрос всегда передаётся `network_distance: [2]`. Город является поисковым сегментом и мягким
сигналом политики, но не блокирует кандидата.

Для recruiter и technical сохраняются независимые cursor-потоки с индексом термина. Термин меняется
после отсутствия `next_cursor` либо после двух пустых cursor-страниц подряд; после всех терминов
выбирается следующий город. Последовательность отправок:

`R, R, T, R, R, T, R, R, T, R`.

После страницы с eligible-кандидатами поиск останавливается. Кандидаты помещаются в небольшую
очередь, после чего выполняется:

`SQL sending claim -> profile preflight -> invitation POST -> подтверждение -> SQL history`.

Подтверждением служит проверенный ответ Unipile V2: HTTP 201, `RelationRequest`, тип `sent`,
непустой ID заявки и совпадающий адресат, если он указан в ответе. Только после сохранения
подтверждения растёт счётчик квоты. При потерянном или неподходящем ответе остаётся проверка
через список заявок и профиль. Повторять неопределённый POST нельзя.
Новая поисковая страница нужна только при отсутствии подходящего кандидата в очереди.

Неиспользованный остаток последнего успешного прогона можно перенести на следующий день:
тот же аккаунт, stack и режим, не более 100 кандидатов, возраст до 36 часов от исходного поиска.
Повторно проверяются каталог, история, а перед POST — текущая роль, профиль и доступность отправки.
Неполный текущий профиль не разрешает отправку перенесённому кандидату.

Перед каждой рассылкой сохраняется сверка ранее отправленных заявок. `pending-reader.ts`
читает либо полный список, либо страницы до конкретной найденной заявки; отсутствие подтверждает
только полный валидный список. `pending-snapshot.ts` принимает свежий полный снимок этой сверки
для того же аккаунта. TTL — пять минут от начала чтения; частичное подтверждение его не продлевает.
Для конкретного кандидата полный свежий профиль может заменить повторное чтение всего списка.
Адаптер проверяет привязку к аккаунту и человеку, поля профиля и время данных:
`X-Cache: MISS/BYPASS` либо `HIT` с известным `Age`, не старше пяти минут.
Неполный профиль, неизвестный возраст или старые данные требуют обычного полного списка.
Краткий сбой profile GET до отправки не сбрасывает пригодный список; возраст проверяется после ожидания.
Отрицательный read-back передаётся следующему обработчику один раз, с проверкой аккаунта,
кандидата, времени отправки и TTL. Неопределённый POST по-прежнему повторять нельзя.

При восстановлении выполненной замороженной нормы сначала сверяется история, затем прогон
заканчивается без подготовки новых отправок. Отправщик создаётся только для первого кандидата.
Проверка аккаунта и собственного профиля повторяются раздельно. В продолжении того же дневного
прогона замороженное число контактов можно использовать повторно только при совпадении
аккаунта, владельца и времени последней верификации. Сам аккаунт всё равно проверяется.
`logger.ts` связывает физические запросы с прогоном до общей очереди и пишет расходы
по операциям, включая повторы и использование снимков. Измерения и команды воспроизведения приведены ниже.

## Pacing и retry

- Между Search-запросами — случайно 40–70 секунд.
- Не более пяти Search-запросов за скользящие десять минут.
- Между фактическими invitation-циклами — случайно 20–180 секунд.
- Между началами физических запросов Inviter — случайно 6,5–11 секунд;
  интервал выбирается при исполнении очередного запроса. Числовая настройка
  общей очереди и поведение других фич остаются прежними.
- Отсев кандидата до POST не назначает новую паузу. Реальная попытка POST назначает её,
  даже если провайдер отклонил запрос. Выбранный срок хранится в `search_progress_json`.
  После восстановления используется остаток сохранённой паузы; если история новее
  сохранённого состояния, назначается полная пауза, чтобы не допустить серии отправок.
- Search timestamps и оба cursor-потока сохраняются в `search_progress_json`.

Для последовательных Unipile `429` используется задержка:

`3 -> 6 -> 12 -> 24 -> 30 минут`.

`Retry-After` задаёт нижнюю границу, если он больше расчётной. Успешная операция сбрасывает attempt.
Остальные transient-сбои используют общий линейный retry. Stop проверяется не реже раза в секунду.
Серия backoff для `invitation_write` хранится отдельно от активного retry read-back: временный сбой
pending/profile-чтения не сбрасывает накопленный шаг `3 -> 6 -> 12 -> 24 -> 30 минут`.

Invitation POST не повторяется вслепую:

- `429` требует отрицательного pending read-back до повторной отправки;
- после задержки обязательны повторный pending/profile preflight и проверка сохранённого `sending`;
- timeout, unreachable и `5xx` переводят запись в `uncertain`, повторяется только read-back;
- deterministic `4xx` отклоняет кандидата;
- База обязана подтвердить `sending` до внешней отправки.

## Состояние и PostgreSQL

Backend передаёт `createSqlInviterStore` через `sqlAppOptions`. Сервис требует явно переданное
хранилище и не выбирает запасной адаптер. Бизнес-логика работает через `ConnectionInviterStore`;
SQL-запросы, транзакции и ограничения доступа остаются в `storage-postgres`.
Новые поля используют существующий `search_progress_json`; миграции схемы не нужны.
Ошибки хранения отмечаются как `storage`. Повтор разрешён только для явно временного сбоя чтения;
неизвестный COMMIT или сбой записи не превращаются в автоматический повтор транзакции.

- `linkedin_connection_search_catalog` — каталог городов.
- `linkedin_connection_runs` — один запуск на `platformAccountId + localDate`.
- `linkedin_connection_history` — lifetime-запись на `accountId + personId`.

Skipped-профили не создают history rows. Lifetime-блокируют только `sending`, `sent`, `pending`,
`accepted` и `uncertain`. Подтверждённые `sent/accepted` history rows являются единственным
источником дневной квоты. Realtime-прогресс передаётся через SSE, а search reservation, фактические
search timestamps, location ID и cursor сохраняются критически для безопасного restart.

`completed` выставляется только при точном совпадении обеих подтверждённых квот. Полное исчерпание
городов даёт `partial / search_exhausted` с точным недобором. Stop сначала проходит через account gate
и выполняет обязательный read-back `sending/uncertain`; повторный invitation POST вслепую запрещён.
Live writer требует стабильный ID. Обычные checkpoints выполняются не чаще раза в 120 секунд;
длинные timer/reservation сохраняются до ожидания и защищают lease без отдельного heartbeat-запроса.
Во всех terminal-состояниях lease освобождается.

### Что изменено

1. Предыдущие отправки по-прежнему сверяются перед каждой рассылкой.
   Полный список передаётся отправщику; немедленной повторной загрузки нет.
2. Перед каждым POST профиль по-прежнему читается. Полный профиль с подтверждённой
   свежестью позволяет проверить наличие заявки у конкретного человека без повторной
   загрузки всех страниц. При неполных или устаревших данных остаётся прежняя проверка списка.
3. Проверенный HTTP 201 с `RelationRequest`, типом `sent` и ID заявки подтверждает отправку.
   Потерянный ответ, чужой адресат или неправильная форма ответа требуют проверки результата;
   повторного POST по неопределённому результату нет.
4. При поиске одной отправки чтение заканчивается на найденной странице.
   Отсутствие заявки подтверждает только полный корректный список.
5. Ошибка собственного профиля не повторяет уже успешный запрос аккаунта.
   При продолжении дневного прогона используется сохранённое число контактов,
   если аккаунт, владелец и время верификации не изменились.
6. Пригодный остаток очереди можно использовать в следующем прогоне: тот же аккаунт,
   stack и режим, до 100 кандидатов не старше 36 часов; текущая роль проверяется заново.
7. Пропущенный до POST кандидат не назначает ещё одну случайную паузу.
   Реальная попытка отправки сохраняет интервал 20–180 секунд. После сбоя возможна
   дополнительная осторожная пауза, если последняя отправка новее сохранённого таймера.
8. Физические запросы, страницы, повторы и использование сохранённых данных видны
   в журнале и привязаны к прогону и аккаунту до общей очереди запросов.

### PostgreSQL

Обе версии проверяются с настоящим SQL-адаптером и подставным транспортом базы.
SQL-режим использует те же таблицы и преобразования строк, что обычный backend.
Выполнены отдельные проверки восстановления квоты, состояния очереди, верификации
аккаунта и паузы после повторного создания адаптера.

Сервис больше не подставляет хранилище, если его забыли передать.
Логи повторов чтения SQL используют `storage`. Неизвестный результат COMMIT,
ошибка записи и сырой сетевой сбой не разрешают повторить транзакцию или приглашение.
В SQL-адаптере отсутствует фиктивный метод сброса HTTP-бюджета старого хранилища.

Тесты используют искусственные данные. Подключений к рабочей базе и реальных
LinkedIn-отправок не было. Схема БД, ENV, интерфейс и оркестратор не меняются.

кэша Unipile. При неизвестной свежести выполняется больше проверок, а не ослабляется защита.

### Обнаружено при подготовке живого теста

Unipile может не вернуть `relations_count` даже для подтверждённого владельца.
В этом случае до расчёта нормы читается полный список контактов, по 100 записей
на страницу. Подписчики и число контактов из старого дня не подменяют это значение.
Повреждённая страница, цикл курсора или неполная выдача останавливают запуск.
Повторяется только неудачная страница; Stop проверяется между страницами.
Если число контактов есть в профиле, дополнительных запросов нет.

Интервал физических запросов самого Connection Inviter — случайно 6,5–11 секунд:
не более 10 начал запросов за скользящую минуту. Лимиты и очереди других фич не меняются.
Ответ 429 по-прежнему включает штатное ожидание; интервал не гарантирует отсутствие
429 при запросах других процессов к тому же аккаунту.
