# LinkedIn Profile Filler

## Задача

Profile Filler строит профиль из подтверждённого английского CV, показывает точный Preview,
последовательно применяет его к собственному LinkedIn-профилю ученика и завершает задание
только после полного read-back.

## Последовательность

1. Backend проверяет LinkedIn-аккаунт и получает актуальное CV.
2. OpenAI извлекает факты. Backend присваивает работам `exp_N`, учёбе `edu_N`.
3. Модель возвращает Headline, About, Open to Work, 100 уникальных Skills и текстовые
   дополнения для каждого fact ID.
4. Backend требует все ожидаемые ID без пропусков, повторов и неизвестных записей.
5. Компания, должность, даты, location, workplace type, школа, степень, направление,
   grade и activities копируются из CV, а не из ответа модели.
6. До двух repair-запросов получают только проблемные разделы и fact ID. Оставшаяся
   фатальная ошибка блокирует Preview.
   Repair сохраняет дубли и неизвестные ID до проверки; объединение не скрывает ошибочный ответ.
   Полнота ID проверяет результат дополнения, а не качество первого извлечения:
   перед live Apply отдельно сверяются исходное CV и извлечённые работы/образование.
7. Backend читает профиль, разрешает обязательные и доступные entity ID Unipile V2 и строит Preview.
8. Администратор подтверждает сохранённый `planHash`; браузер не присылает новый план.
9. Backend выполняет один PATCH на шаг и свежий read-back.
10. `succeeded` ставится только после полного совпадения; иначе продолжаются только чтения.

## Поля

- Headline и About.
- Experience: company, job title, dates, location, workplace type, description и Skills.
- Education: school, degree, field of study, dates, grade, activities, description и Skills.
- Skills: существующие сохраняются, добавляется только недостающее до 100.
- Open to Work: только с подтверждёнными job title и location ID.

Для `COMPANY`, `JOB_TITLE`, `LOCATION` и `SCHOOL` используется точный ID каталога,
когда найдено единственное совпадение. Иначе фактические названия Experience/Education
передаются по имени. `degree` и `field_of_study` передаются по имени и проверяются read-back.
Skills нормализуются, дедуплицируются и передаются по имени без запросов каталога. Существующие
Skills сохраняются, а новые добавляются только до общего лимита 100. Skills, прикреплённые к
Experience/Education, входят в тот же набор.

Даты сохраняют точность CV: год без месяца остаётся годом. Если Unipile требует
отсутствующий месяц, создание блокируется; для существующей записи совпадающий год
можно подтвердить, не меняя её дату. Сопоставление учитывает LinkedIn ID,
компанию/должность/даты, а для образования — также степень и направление.
Лишние существующие работы не удаляются: Preview показывает предупреждение.
Один LinkedIn ID не может соответствовать двум фактам CV. Конфликт блокируется при построении
Preview и повторно перед Apply сохранённого плана, включая старые Preview.

`end_date: present` означает явно указанную в CV текущую работу или учёбу; неизвестная дата
остаётся неизвестной. Backend хранит этот признак отдельно от даты. Если LinkedIn возвращает
дату окончания для текущей записи, Apply блокируется: V2 не документирует безопасное снятие
этой даты. Нужно отметить запись текущей в LinkedIn и создать новый Preview.

Нехватка места для Skills не блокирует другие поля. В прикреплённые Skills попадают
только навыки из итогового набора, без искусственных замен. Точный список пропусков
сохраняется в предупреждениях; итог — `needs_expert_review / partially_completed`.

## Запись и проверка

- Изменения идут последовательно в порядке MCP-контракта.
- Под общим account gate перед Apply проверяются свежие identity, состав записей и Skills.
  Изменившийся состав требует нового Preview. Перед каждым PATCH выполняется свежая проверка.
- Намерение записи и ожидаемый результат сохраняются до PATCH. Ошибка сохранения
  запрещает запись; ошибка сохранения после PATCH разрешает только read-back.
- После PATCH выполняется пауза 2–3 минуты; общий интервал между Skill-пакетами — 3–5 минут.
- Read-back запрашивает только изменённые разделы и использует `Cache-Control: no-cache`.
- Отложенные чтения назначаются на отметки 5, 15, 30 и 60 минут от начала проверки,
  а не через суммирующиеся интервалы. Полный `Retry-After` сдвигает чтение, если нужно ждать дольше.
- `throttled_sections` означает временно недоступный раздел, а не отсутствие данных.
- Timeout, `5xx` и потерянный ответ не приводят к повторному созданию Experience/Education.
- Неопределённый PATCH и неподтверждённые create/Skills блокируют следующие записи.
  Восстановление сохранённого намерения после рестарта выполняет только чтения.
- Старый сокращённый payload-retry удалён: location, Skills, grade и activities не отбрасываются.
- Состояние `verifying`, номер попытки и `nextReadBackAt` сохраняются в существующем
  `result_json`. После перезапуска backend продолжает чтения без повторного PATCH.
  Восстановление запускается при старте backend без открытия консоли. Оно выбирает только
  `running/verifying` с сохранённым намерением записи и незавершённой проверкой; старые
  задания генерации не возобновляются. Занятый gate повторно проверяется через 30 секунд
  без нового чтения списка Noco; сохранённые таймеры и `Retry-After` не сбрасываются.
- GET задания и истории только читают данные и показывают состояние прерванного задания.
  Они не сохраняют статус и не запускают проверку. Восстановление выполняет отдельный
  `recoverPending` при разрешённом запуске backend; режим `read-only` его не вызывает.
- После последней неудачной проверки статус становится `needs_expert_review` с перечнем
  неподтверждённых разделов.

Обычные надписи и ожидание отправки обновляют память backend. Внутренний `onProgress`
явно различает `memory` и `checkpoint`; по умолчанию состояние сохраняется.
На отправляемый шаг — два сохранения: намерение до PATCH и результат с таймером read-back.
Подтверждение шага включается в следующее сохранение. Расписание финальной проверки остаётся
в Noco; её успешный результат сохраняется вместе с окончательным статусом задания.
Начало Apply записывается вместе с первым намерением. Сбой до него не приводит к отправке:
после рестарта остаётся Preview для повторного ручного Apply со свежей проверкой.
Неопределённость, ошибки и новые сроки повторных проверок сохраняются отдельно. Ошибка Noco
после PATCH запрещает следующие записи; текущий read-back сохраняет полученный cooldown
в памяти. Уже сохранённые таймеры восстанавливаются после рестарта. Payload не сокращается.

## Чтения и подготовка

- Profile Filler получает выбранный аккаунт и связанные с ним записи, не все таблицы.
  Полученный аккаунт передаётся в генерацию и Preview. Перед Apply данные читаются заново
  без кэша, вместе с проверкой Unipile identity и актуального профиля.
- CV выбирается прежним правилом из записей только этого ученика; файл загружается один раз.
  При загрузке собственного CV таблица CV не читается. Нового кэша нет.
- Генерация сохраняет создание задания, готовый проверенный документ для восстановления
  и Preview; обычные стадии — в памяти. Ошибки и catalog retry остаются в Noco.
- История принимает необязательный `platformAccountId` на прежнем GET `/profile-jobs`.
  Без параметра поведение прежнее; активные задания проверяются отдельным свежим запросом
  выбранного аккаунта. Завершение обновляет историю полученным snapshot без повторного GET.
- Два успешных шага: 3 сохранения подготовки + 6 выполнения вместо прежних 8 + 1 + 9.
  На mock из 201 записи чтения аккаунта, CV и истории: 18 → 6 HTTP-запросов при холодном кэше.
  Это проверочные сценарии, не фиксированный бюджет live-запуска. Общий Noco-клиент не меняется.

## Безопасность интерфейса

- Разные ученики заполняются параллельно в одном backend. Для каждого аккаунта —
  собственные CV, Preview, подтверждение и один цикл наблюдения. Сворачивание окна
  и переключение ученика не останавливают задания. После reload открытие карточки
  восстанавливает её активное задание чтением, без повторного Apply.
- Одновременные записи одного аккаунта запрещены общим account gate. Все задания
  используют прежние ограничители Noco и Unipile; параллельность их не обходит.
  Работа нескольких backend на разных машинах с одним аккаунтом не поддерживается.
- Preview из CV нельзя редактировать или пересобрать как ручной JSON. Доступна только новая
  генерация из CV.
- Apply разрешён только для сохранённого Preview без фатальных ошибок.
- Устаревший Preview, недоступный раздел и неоднозначность возвращают понятную ошибку `409`;
  ошибка сохранения состояния — `503` с запретом дальнейших записей.
- Ключи, cookies, CV и полные ответы провайдеров не попадают в Preview и безопасные логи.
- Ручной `profile.json` остаётся отдельным диагностическим входом и проходит общий валидатор.
- Финальное сообщение: `Profile completed and verified`.
- Для пропусков Skills: «Профиль заполнен частично»; для неподтверждённых записей —
  отдельное объяснение без сообщения об успехе. История и reload возобновляют один
  цикл наблюдения; временная ошибка чтения не выключает его. Таймер работает и в `verifying`.

Общий ограничитель Noco считает фактические HTTP-попытки: после завершения каждого
четвёртого запроса, включая ошибку, выдерживается минимум секунда. Кэш не расходует
пачку; cooldown после `429` действует на общую очередь.
