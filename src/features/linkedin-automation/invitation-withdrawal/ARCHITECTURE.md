# Отзыв старых приглашений

Администратор выбирает ученика в LinkedIn-консоли, открывает «Отозвать старые
приглашения» и загружает список. Unipile возвращает все ожидающие отправленные
приглашения аккаунта, включая ручные. Читаем все страницы, не историю Inviter.

Показываем дату отправки и число прошедших дней. Отзываем только приглашения,
которые строго старше 14 дней. Ровно 14 дней, будущая, отсутствующая или
некорректная дата не разрешают отзыв. Используем `created_at` из Unipile V2,
не угадываем дату по надписям вроде «3 weeks ago».

## Запуск

- Список действует 10 минут. Для запуска нужно отдельное подтверждение.
- Перед началом снова проверяем аккаунт и владельца. Полный список берём из
  подтверждённого просмотра, не загружаем повторно. Просроченный токен или
  изменившаяся привязка аккаунта не разрешают запуск.
- Отзыв идёт по одному с отдельной случайной паузой 2–13 секунд между отзывами.
  Чтения и сеть могут увеличить фактическое время между запросами.
- Успешный отзыв — HTTP 200 с `object: RelationRequestCanceled`. ID и счётчик
  сохраняем до следующего POST. После всех успешных отмен одним полным списком
  проверяем исчезновение всех этих ID. Если хотя бы один ещё виден, повторяем
  только чтение через 1 и 2 секунды: всего до трёх проверок. Ошибка общей сверки
  оставляет запуск неподтверждённым; сохранённые ответы отмены не теряются.
  При `429` чтение ждёт окончания сохранённой паузы; другие ошибки останавливают
  очередь. Запрос отзыва никогда не повторяется.
- Stop завершает доступную проверку уже начатого отзыва и не начинает следующий.
  Если Unipile ограничил чтения, Stop прерывает ожидание. Непроверенный отзыв
  остаётся в журнале для кнопки «Проверить результат» после окончания паузы.
- «Свернуть» скрывает окно, не останавливая очередь. В строке ученика остаются
  статус и число отзывов; «Открыть отзыв» возвращает к подробностям. Можно запустить
  другого ученика: очереди независимы, Stop действует только на выбранного.
  После обновления страницы или поиска ученика состояние снова читается с backend.
- При `429` используем расчёт паузы из Inviter: 3, 6, 12, 24, затем 30 минут.
  Больший `Retry-After` соблюдаем полностью. Номер попытки и срок сохраняем до
  ожидания. Успешное чтение сбрасывает паузу; только после сохранения продолжаем.
- После паузы проверка и подтверждённая очередь продолжаются без нового нажатия.
  В окне и свёрнутой строке виден статус ограничения Unipile, в окне — время
  продолжения. Stop работает во время ожидания; reload не запускает новую очередь.
- Если `429` вернул сам POST, после паузы только проверяем список. Исчезнувшее
  приглашение отмечаем «уже не ожидает», считаем пропуском и идём дальше.
  Это не доказательство нашего отзыва: заявку могли принять или убрать вручную.
  Такой же контрольный пропуск разрешён после ответа 404/410, если полный список
  подтверждает отсутствие ID. Если приглашение осталось — останавливаемся
  с неопределённым результатом, не повторяя POST. Timeout и прочие ошибки
  не получают автоматического повтора.
- Новые приглашения, которых не было в подтверждённом списке, не добавляются в очередь.
- При неопределённом результате доступна кнопка «Проверить результат». Она сверяет
  владельца и полный список для всех сохранённых успешных отмен и текущего
  неизвестного результата. Неизвестный результат при исчезновении становится
  пропуском, а не подтверждённым отзывом. Повторное нажатие не увеличивает счётчик
  второй раз. Старые журналы без поля `confirmed` читаются по прежнему `current`,
  но исчезновение без ответа отмены тоже не считается доказательством отзыва.
  Ошибка сохранения не показывается как успех. Если приглашение всё ещё видно,
  неопределённость остаётся.
- Такая проверка не отзывает приглашения и не продолжает очередь. После успешной
  проверки незавершённая очередь получает статус «Остановлено», полностью
  выполненная — «Очередь завершена». До проверки новый запуск запрещён, чтобы
  не затереть неподтверждённый результат. GET статуса остаётся только чтением журнала.

## Ответственность файлов

- `policy.ts` — возраст приглашений и паузы.
- `service.ts` — список, подтверждение, запуск, Stop и состояние.
- `execution.ts` — последовательный отзыв и проверка результата.
- `readback.ts` — ограниченная проверка исчезновения всех заданных ID.
- `retry.ts` — сохранение паузы Unipile, ожидание со Stop и повтор только чтений.
- `recheck.ts` — повторная проверка сохранённого результата, без новых отзывов.
- `file-store.ts` — журнал перед каждой отправкой и итог.
- `compose.ts` — подключение к существующему Inviter, выбранному хранилищу аккаунтов
  и общей блокировке операций аккаунта.
- `src/integrations/unipile/invitation-withdrawal.ts` и `sent-invitations.ts` — API и страницы.
- `invitation-withdrawal-routes.ts`, `InvitationWithdrawal.vue` — backend и интерфейс консоли.

Новых таблиц нет. Журнал хранится в `storage/linkedin-invitation-withdrawal`, вне Git.
Намерение сохраняется до POST. Начатые ID больше не отправляются, даже если ответ
потерян. В запуске сохраняются `confirmed` (успешные ответы отмены),
`noLongerPending` (пропуски без подтверждения отмены) и `checkedAt` (общая сверка).
Журнал нельзя удалять или забывать при переносе работающего backend.
После перезапуска нет автоматического продолжения: виден прерванный запуск;
новый список пропускает ранее начатые отзывы. Неопределённый результат требует
проверки через «Проверить результат», кнопки повторного отзыва нет.

Используем существующие writer-enabled, writer ID и локальную блокировку Inviter.
Два компьютера с одним LinkedIn-аккаунтом по-прежнему не поддерживаются.
Историю отправок и дневную квоту Inviter отзыв не уменьшает. Схемы Noco/SQL,
HH, CRM, Dolphin и другие фичи не меняются.

## API

Все маршруты требуют администратора. Основа:
`/api/admin/linkedin/accounts/:id/invitation-withdrawal`.

- `GET /preview` — полный список, дата, возраст, причина пропуска и токен подтверждения.
- `GET` — состояние последнего запуска, без обращения в LinkedIn.
- `POST {token, confirm: true}` — запустить подтверждённую очередь.
- `POST /stop` — остановить очередь.
- `POST /recheck {runId}` — перепроверить конкретный запуск и сохранить результат;
  требует права writer и той же блокировки аккаунта, что и отзыв.

В mock-режиме работают подставные данные. При передаче подставного адаптера
Inviter отзыв отключён, если его адаптер и журнал не переданы явно.

## Проверка

На Node 24.20.0: `npm run linkedin:withdrawals:test`,
`npm run linkedin:withdrawals:e2e`, `npm run linkedin:connections:test`,
`npm run linkedin:web:test`, `npm run typecheck`, `npm run web:build`.
Браузерный тест проверяет просмотр, подтверждение, Stop, reload, сворачивание,
две независимые очереди, повторную проверку, ошибку сохранения и автоматическое
продолжение после `429`. Длительные паузы проходят с тестовыми часами.
Это не доказывает успешный реальный отзыв.

### Расход запросов

Сравнение с Withdrawal на `247428e`, на одном подставном наборе: 300 ожидающих
заявок, 40 старше 14 дней, страницы по 100 с `total_count`, без задержки видимости
и ошибок. Получатели отмен и оставшиеся заявки совпадают.

| Операция | До | После |
| --- | ---: | ---: |
| Загрузка для просмотра | 3 | 3 |
| Проверка аккаунта и владельца | 2 | 2 |
| Повторный список перед стартом | 3 | 0 |
| Отмены | 40 | 40 |
| Контрольный список | 120 | 3 |
| Всего | 168 | 48 |

Экономия на этом сценарии — 120 запросов (71,4%). Это замер обращений к mock HTTP,
а не обещание одинакового процента на любом аккаунте: число страниц, ошибки,
задержка видимости и неоднозначные ответы добавляют чтения. Регрессия на 48
запросов закреплена в `src/integrations/unipile/invitation-withdrawal.test.ts`.

Контракт: [Unipile V2](https://developer.unipile.com/v2.0/docs/linkedin-manage-invitations).
`created_at` необязателен; его наличие на конкретном аккаунте нужно проверять чтением.
После отзыва LinkedIn может запретить повторное приглашение тому же человеку
на срок до трёх недель.
