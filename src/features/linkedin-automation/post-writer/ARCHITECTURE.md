# LinkedIn Post Writer

## Проверка неизвестной публикации

Первичная проверка после успешного POST остаётся через пять секунд. Для не найденного
результата интервалы растут от времени исходной попытки: пять минут в первые 15 минут,
затем 15 минут до часа, раз в час до суток, затем раз в шесть часов. Ошибка чтения
не возвращает старое задание к частым проверкам. Более длинный Retry-After сохраняется.
Первоначальная краткая пауза после ошибки свежего POST остаётся прежней.
Абсолютный `nextActionAt` хранится в прежнем состоянии задания и переживает рестарт.
Известный ID проверяется напрямую; неизвестный результат и защита от повторной
публикации не удаляются. Stop прекращает отправки и дальнейшие проверки; неизвестный исход остаётся в истории.

## Запуск

| Способ | Подтверждение |
| --- | --- |
| По расписанию | Никогда: тема → текст → проверки → публикация |
| Вручную с подтверждением | Approve для конкретного contentHash |
| Вручную без подтверждения | Публикация после проверок |

Ручной выбор не влияет на расписание. По умолчанию расписание, мемы и лайки выключены,
ручной режим — с подтверждением. Непроверенный контент не публикуется ни в одном режиме.

## Выбор аккаунтов для лайков

Реакции выбранных аккаунтов проверяются одним списком перед серией; пригодный снимок
живёт не более пяти минут и привязан к читающему аккаунту, посту и списку исполнителей.
Успешный `PostReactionAdded` сохраняется до следующего лайка. В конце одна общая сверка
подтверждает всех исполнителей. Ошибка сверки и перезапуск не разрешают повторный POST.
Неизвестный ответ без подтверждённой квитанции по-прежнему проверяется до продолжения.
Проверка личности разрешает кэш провайдера; сверка публикации и реакций всегда свежая.
В mock HTTP-сценарии шести лайков: 30 → 20 запросов, из них чтения реакций 12 → 2;
получатели и подтверждённые результаты совпадают. При устаревании снимка или ошибках
потребуются дополнительные чтения. Без `Retry-After` пауза Post Writer после 429 — 90 секунд.

`settings.likeAccountIds` — ID выбранных подключённых аккаунтов. Список валидируется по источнику Post Writer;
автор, неизвестные аккаунты и повторные реальные LinkedIn ID не допускаются. Read-only API
`GET /api/admin/linkedin/accounts/:id/post-writer/like-accounts` возвращает только ID и имена доступных исполнителей.
Для выбранного списка цель — по одному лайку от каждого уникального аккаунта, без добора посторонних.
При отключении выбранного аккаунта он пропускается прежней проверкой доступности.

Очередь фиксирует выбор в `engagement.accountIds` и сохраняется при перезапуске. Ручное продолжение использует ту же очередь.
Удаление участника из настроек запрещает его следующий автоматический POST, но не отменяет проверку уже отправленного.
Новые участники не добавляются в начатую очередь. Ручной запуск использует выбор, сохранённый на момент нажатия;
дальнейшие изменения настроек не меняют эту разовую очередь.

Старые настройки без `likeAccountIds` продолжают прежний случайный выбор 6–7 аккаунтов до явного изменения.
Интерфейс подписывает этот режим; при новом включении лайков требует выбрать исполнителей.
Поля хранятся в существующем JSON состояния, без новой схемы БД.

## Расписание

### Готовые посты на неделю

В настройках ученика есть отдельный режим «Готовые посты на неделю».
Выберите неделю по МСК, вставьте тексты в нужные дни и сохраните настройки.
Пустые дни пропускаются. Включённая автопубликация использует прежние интервалы
времени, но не галочки дней генерации из CV. Один пост — не больше 3000 знаков.

Текст не переписывается, CV не читается. Для каждого поста создаётся мем из его
текста; ошибка мема не разрешает отправить один текст. Общие и личные запреты
остаются в силе. Генерация из CV работает по-прежнему в своём режиме.

Чтобы отправить готовый текст сразу, выберите день, сохраните план и нажмите
«Опубликовать сейчас». После подтверждения Writer создаст мем и отправит пост.
Включать расписание не нужно; часы автопубликации не ограничивают ручной запуск.
Подходит сегодняшний или будущий день. При несохранённых правках кнопка недоступна.
Ручной запуск и расписание используют один ID дня: двойной клик, перезапуск или
наступление выбранной даты не создают второй пост. Stop и неизвестный результат
отправки тоже не разрешают повторную публикацию этого дня.

План хранится в `state_json` настроек, копия начатого поста — в задании.
Новые таблицы и колонки не нужны. Будущие тексты можно править; начатый текст
не меняется. Очистка плана не останавливает уже начатые задания — для них есть Stop.
Повторное сохранение и перезапуск не разрешают второй пост на ту же дату.
Пропущенные дни не публикуются задним числом. Перед возвратом на старую версию
кода отключите автопубликацию готовых планов: старый код не знает этот режим.

### Генерация из CV

- Галочки Пн–Вс и переключатель автопубликации в настройках ученика.
- Один запуск в выбранный день, случайное время внутри интервалов по МСК.
  Начальный интервал — 10:00–15:00. Интервалы можно добавлять, менять и удалять;
  пересечение и переход через полночь запрещены.
- Время сохраняется один раз. После restart остаётся прежним.
- Пропущенный запуск допускается только внутри оставшихся интервалов того же дня.
- Изменение настроек пересчитывает только не начатое время. Дневной ID не меняется,
  поэтому правка интервалов и restart не разрешают второй автоматический пост.
- Пока есть незавершённая публикация (включая awaiting_approval), второй запуск не создаётся.
  Ожидающие лайки опубликованного поста не занимают автора; блокируется фактический исполнитель лайка.
- Окно относится к началу генерации, не ограничивает ручные действия и завершение работы.
- Выключение расписания отменяет будущие запуски; Stop относится к текущему заданию.

## Подготовка контента

Если готовое английское CV отсутствует (`profile_cv_not_ready`), используется
сохранённый основной стек ученика. Контекст помечен `source: stack`, содержит пустой
список личных фактов и предупреждение `post_cv_missing_stack`. Предупреждение
сохраняется в прежнем JSON задания, показывается в карточке поста и журнале оркестратора.
Это не ошибка и не требует ручного разрешения на каждый запланированный пост.

В этом режиме разрешены нейтральные технические объяснения и явно гипотетические
примеры по стеку. Личный опыт, работодатели, проекты и достижения не выдумываются;
персональные утверждения и цифры блокируются. Тема и текст обязательно проходят
существующую смысловую проверку; запреты, длина, язык и защита от повторов сохранены.
Без указанного стека возникает `post_stack_missing`. Ошибки SQL, загрузки имеющегося
CV и модели не маскируются этим режимом. После появления готового CV следующий
пост снова использует его; начатый пост сохраняет свой контекст при перезапуске.
Готовые тексты на дату и явно загруженное CV обрабатываются по прежним правилам.

Ответственность разделена между четырьмя частями:

- Подготовка данных получает CV, факты и историю. Загрузчик, выбор CV и извлечение
  фактов передаются снаружи; конкретные клиенты подключает `runtime.ts`.
- `writePost(input, model, options?)` выбирает тему, пишет и проверяет текст.
  Вход — готовый контекст и история без ID базы и аккаунта. Выход — `ready`,
  `blocked` с причинами или `cancelled`; ошибка провайдера передаётся отдельно.
  Writer не меняет вход, не хранит состояние между вызовами и не обращается к базе,
  ENV, CV-загрузчику или LinkedIn. Для самостоятельного вызова достаточно модели и данных.
- Управление запуском сохраняет результат и ведёт расписание, Approve, Stop и SSE.
- Публикация и реакции выполняются отдельными исполнителями с узкими интерфейсами.

Необязательные `options`: сигнал отмены, контрольная точка и асинхронный обработчик
её сохранения. Контрольная точка содержит темы, выбранную тему, черновик, ошибки
и число зарезервированных исправлений. Следующий запрос ждёт успешного сохранения.
Если сохранение резерва не удалось, Writer возвращает попытку и передаёт обработчику
исправленную контрольную точку. Управление запуском заменяет ею очередь сохранения;
до её записи генерация не продолжается. В обычном сценарии новых запросов к Noco нет.
После рестарта готовый черновик проверяется локально, тема не выбирается заново.
Потерянный ответ на repair не обнуляет общий предел двух исправлений. Отмена
останавливает дальнейшую генерацию; уже начатую публикацию по-прежнему проверяет внешний процесс.
При аварийном завершении до сохранения возврата остаётся прежний резерв: безопаснее
потерять неподтверждённую попытку, чем превысить общий предел после неизвестного запроса.
Состояние Writer хранится в прежних полях run; схема Noco не меняется.

Своя тема передаётся в `rules.requestedTopic`; автоматический выбор в этом случае
не вызывается. Неустранимая ошибка темы блокирует результат, а не подменяет тему.
Общие и личные запреты объединяются. Проверяется смысл темы и готового текста
через переданный метод `model.review`; запрет, сомнение или невалидный ответ блокируют
результат. Без своей темы и запретов дополнительных запросов проверки нет.
Сохранённый результат проверки привязан к тексту, контексту и правилам.
Изменение запретов отменяет прежнее подтверждение и требует повторной проверки.

Backend получает аккаунт и финальное английское CV по записи cv_processing в Noco.
Файл читает существующий read-only Drive-загрузчик. Факты кэшируются в Noco
по ревизии CV и хэшу файла. Каталог Skills не вызывается, Profile Filler не изменяется.
Для отдельного запуска можно загрузить PDF/DOCX до 15 МБ. Он сохраняется файловым
адаптером, а ссылка и снимок контекста — в run. Исходное CV ученика не заменяется.

Модель предлагает 3–5 тем. Backend исключает повторные сигнатуры, выбирает лучшую
по оценке соответствия контексту и запрашивает текст. Максимум два repair.
Проверки: структура ответа, fact IDs и claims, числа, язык, длина, хэштеги,
запрещённые формулировки и текстовые повторы. Они не доказывают семантическую точность
модели: качество фактов, причинных связей и новизны требует отдельного разрешённого eval.

Роль и редакционные требования: [CONTENT_POLICY.md](./CONTENT_POLICY.md).
Responses API: Structured Output, store=false, без tools. Два основных запроса:
темы и текст; извлечение фактов — только при изменении CV. Для своей темы выбор
тем пропускается. Проверка запретов выполняется той же настроенной моделью, без
второй постоянной модели. Это дополнительная смысловая проверка, не доказательство истины.

## Отдельная подготовка текста

Экран «Writer из своего CV» доступен из консоли и как отдельный `writer.html`.
Автор имеет постоянный ID, роль, уровень, стек, аудиторию, стиль и личные запреты.
Смена CV не меняет автора и не стирает его историю. Получение текста не требует
подключённого LinkedIn-аккаунта. Результат обозначается «Текст готов — не опубликован».

`text-workspace` управляет заданиями и передаёт контекст в тот же Writer. Хранилище
`JsonFiles` передаётся снаружи: сейчас это атомарно заменяемые JSON-файлы с read-back;
для тестов — память. CV и кэш фактов обслуживает отдельный `cv-files`.
Состояние и общий предел repair сохраняются; Stop и Retry-After переживают restart.
Режим не имеет методов публикации или лайков. Выбор другой промышленной БД и
публикация с отдельного сервера остаются отдельной интеграцией, не свойствами Writer.
Переключатель «Подготовить мем вместе с текстом» добавляет тот же мем-процесс;
готовые текст и картинка остаются локально и никуда не публикуются.

Общие запреты действуют в пределах своего хранилища: настройка Noco — для карточек,
локальная — для независимых авторов. UI явно различает эти пространства.
Параллельная запись одного локального хранилища с разных компьютеров не поддерживается.
Два локальных текстовых writer блокируются общей эксклюзивной блокировкой на порту 4440.

## Хранение и API

- `linkedin_post_settings`: ручной режим, расписание, выбранное время, лайки, кэш фактов.
- `linkedin_post_runs`: контекст, версии, проверки, подтверждение, намерение POST, план лайков.
- `linkedin_post_history`: резервация аккаунт + contentHash, пост и ссылка.
- `record_key` — обычное текстовое поле; платные Unique Fields не требуются.
  Один backend последовательно обрабатывает запись каждого ключа: чтение → запись → read-back.
  Существующая резервация не создаётся повторно. Неясный create разрешается только чтением;
  отсутствие строки после timeout не разрешает новый POST. Дубли блокируют работу, не удаляются.
  При запуске проверяются структура и дубли во всех трёх таблицах, включая историю.
- Admin API: `/accounts/:id/post-writer` (снимок), `/settings`, `/runs`, `/events`.
- `POST /accounts/:id/post-writer/prepared-runs`: ручная отправка готового дня.
  Принимает `{ date, text }`, сверяет с сохранённым планом; устаревший текст — 409.
  Повтор возвращает существующее задание. Другой активный запуск — 409.
- Действия: `/post-runs/:runId/approve|reject|stop`. Префикс: `/api/admin/linkedin`.
- `POST /post-runs/:runId/retry-meme`: продолжить старую ошибку описания мема.
  Доступно администратору до попытки картинки и публикации, если у аккаунта нет другого
  активного задания и в истории нет резервации этого запуска. ID и текст сохраняются.
  Кнопка «Продолжить с мемом» есть в результате и истории. SQL вручную не менять.
- Картинка: `GET /post-runs/:runId/meme`, только admin; бинарные данные не входят в SSE.
- SSE: снимок при подключении и изменении, keepalive 15 секунд.
  Таймер считает браузер; fallback polling — 15 секунд.
- Дополнительный текстовый API: `/api/post-writer/text`, `/authors/:id`,
  `/authors/:id/jobs`, `/jobs/:id/stop`, `/jobs/:id/meme`, `/policy`. В консоли нужен admin;
  отдельный сервер требует Bearer token. Наблюдение — раз в 15 секунд, без Noco.
- Общие запреты карточек: `/api/admin/linkedin/post-writer/policy`, запись настроек
  с ключом `0` в прежнем JSON-хранилище. Новые колонки и таблицы не нужны.
- Состояния: queued → generating → awaiting_approval или ready → publishing → verifying → published.
  Дополнительно: blocked, uncertain, rejected, stopped.

## Запись и восстановление

Один writer: `LINKEDIN_POST_WRITER_ENABLED=true` и постоянный `LINKEDIN_POST_WRITER_ID`.
Эксклюзивный порт 4439 предотвращает второй writer на этой машине. Это не распределённая
блокировка: другие машины должны иметь writer выключенным.
При штатном завершении новые операции запрещаются; backend ждёт начатые запросы и
сохранение их результата, затем освобождает порт. Незавершённый read-back восстанавливается
из сохранённого намерения. Принудительное убийство процесса не является штатным завершением.
Гарантия действует для одного сервера записи, не для нескольких независимых машин.

Account gate удерживается во время mutation/read-back, не генерации и ожидания Approve.
Перед POST: identity → сохранение намерения восстановления → резервация с read-back → POST.
Сбой или рестарт между этими шагами не разрешает повтор публикации: только проверку результата.
Публикация: `POST /v2/{account_id}/posts`, собственный аккаунт, публичный текст;
включённый мем передаётся исходным файлом в том же POST через `multipart/form-data`,
поле `attachments[0]`, с MIME и именем файла. Картинка не сжимается и не перекодируется.
Без картинки остаётся JSON. Хранение мемов не меняется: для отправки сохранённый
base64 преобразуется в байты. Формат соответствует [Sending Files](https://developer.unipile.com/v2.0/reference/api-usage#sending-files).
Затем GET с no-cache; проверяются автор, текст и время, а для мема — сохранённый
attachment ID и доступность картинки. Без ID из ответа POST результат остаётся uncertain.
Только после подтверждения — published. V2 POST не описывает alt text: он хранится
для предпросмотра, но не выдаётся за установленный в LinkedIn.
Timeout, 5xx и неизвестный результат не разрешают повтор POST: только read-back.
Restart восстанавливает незавершённые намерения и gate, включая ожидание Retry-After.
Stop запрещает новые POST и GET, включая проверки публикации и лайков. Ответ уже
начатого запроса сохраняется; неизвестный результат остаётся в истории без фоновых проверок.

Полный Retry-After включён опцией только этого адаптера. Noco использует общую очередь,
но feature-local транспорт не повторяет POST. Сбой сохранения блокирует новые записи.
JSONL содержит коды, время, ID запуска и счётчики, без CV, постов, ключей и персональных профилей.

## Лайки

После подтверждения поста выбрать 6–7 разных подключённых аккаунтов, исключая автора.
Сохранить план; отправлять последовательно с паузами 5–90 секунд. Успешные квитанции
сохраняются сразу, подтверждение реакций выполняется общим чтением в конце серии.
V2 reaction=linkedin_like; список LinkedIn-реакций читается через offset, не cursor.
Потерянный ответ даёт uncertain: проверяется тот же аккаунт, POST не повторяется.
Выключение отменяет остаток, не удаляя поставленное. Включение не обрабатывает старые посты.
Статусы поста и лайков отдельные: пост остаётся успешным при недоборе лайков.
Подробная история каждой реакции хранится в run.

Если проверка до отправки вернула `post_account_not_ready`, аккаунт пропускается:
причина сохраняется у реакции и показывается в консоли. После обычной паузы очередь
продолжает оставшийся план, не подбирая замену. Итог при недоборе — «Выполнены частично».
Постоянная ошибка владельца или доступа (400/401/403/404/410/422 без срока повтора)
завершает конкретный лайк с сохранением причины, без фонового опроса. Если отправка
уже началась, результат остаётся неизвестным с `verificationStopped`; повтор запрещён.
Остальные выбранные аккаунты продолжаются, общий итог сохраняет причину недобора.
`429` сохраняет полный срок для
затронутого аккаунта; у общего чтения реакций отдельный таймер. Ошибка после POST
требует проверки того же результата без повторной отправки. Проверки неизвестного
лайка постепенно редеют до одной в два часа; более длинный Retry-After сохраняется.
Автоматическая очередь оркестратора прекращает работу через 24 часа от создания
прогона (общий `AUTOMATIC_RUN_MAX_AGE_MS`), даже если сохранённый срок провайдера позже.
Это локальная остановка, не обход Retry-After: внешних запросов при ней нет.
Неизвестные попытки и их ID остаются в истории с `verificationStopped`.
Разрешение расписания проверяется перед шагом и каждым HTTP-запросом, включая GET
после ожидания в очереди. Перезапуск не продлевает срок и не отменяет Stop.
Ручной запуск лайков сохраняет собственный контракт.
Ошибки исполнителей передаются через `reportLikeEvent` в общий журнал; локальный
JSONL сохраняется. Событие содержит автора, исполнителя, прогон, код и этап
(подготовка, отправка, сверка). Эти же причины видны в карточке прогона.

У опубликованного вручную поста есть отдельная кнопка «Запустить лайки»
(`POST /post-runs/:runId/start-likes`). Она запускает прежнюю очередь один раз,
не публикует пост заново и не меняет настройки будущих постов. Работает и для
«Опубликовать сейчас» в готовом плане. Для постов по расписанию кнопки нет.
Повторный запрос возвращает ту же очередь; отменённую или ранее запущенную
автоматическую очередь он не восстанавливает. Разовые лайки останавливаются
кнопкой Stop, а не галочкой в настройках. Состояние хранится в прежнем JSON задания.

Для старой ручной очереди, остановленной на `post_account_not_ready` до отправки,
кнопка меняется на «Продолжить лайки». Продолжение сохраняет список и подтверждённые
реакции; неизвестные отправки и Stop его запрещают. Сам перезапуск ничего не возобновляет.

## Мемы

Отдельный `writeMeme` получает готовый пост, аудиторию, запреты, историю и переданные
адаптеры модели/изображений/файлов. Сам `writePost` по-прежнему пишет только текст.
Единственный редакционный промпт находится в [MEME_POLICY.md](./MEME_POLICY.md).

- Включение: `LINKEDIN_POST_MEMES_ENABLED=true` и явная модель
  `OPENAI_LINKEDIN_MEME_IMAGE_MODEL=gpt-image-2`; дополнительно включается настройка автора.
  Ключ: `OPENAI_LINKEDIN_MEME_API_KEY`, иначе `OPENAI_LINKEDIN_POST_API_KEY`, иначе
  `OPENAI_LINKEDIN_PROFILE_API_KEY`. Подстановка ключа не включает генерацию автоматически.
- Модель готовит концепцию, код добавляет технические требования, Image API создаёт PNG.
  Неверный формат получает одно исправление; повторная ошибка формата переводит генерацию
  картинки на исходный текст поста с теми же ограничениями. Резервных готовых мемов нет.
- QA получает настоящую картинку и текст через уже настроенную модель Writer с поддержкой
  изображений. При замечаниях — одно улучшение, затем выбор лучшей картинки. Слабая
  релевантность не отменяет публикацию. При сбое QA/улучшения остаётся пригодный оригинал
  с предупреждением. Обычно это три запроса; максимум два описания, две картинки и две QA.
- Намерения и счётчики сохраняются до вызовов. Неизвестная генерация не повторяется
  вслепую; рестарт читает уже сохранённые картинки. Без картинки текст не публикуется.
  SQL-схема и ENV не меняются; новые поля QA хранятся в прежнем JSON задания.
- Изображение проверяется на формат 1024×1280, целостность хранения и hash. QA проверяет
  видимый текст, дефекты и связь с постом, но не гарантирует качество юмора и всех букв.
- `approval_required`: текст и мем показываются вместе; картинка открывается крупно.
  «Мем просмотрен» передаёт `memeReviewedHash` вместе с `contentHash`. Backend требует
  совпадение обоих с текущей версией. После изменения текста/картинки подтверждение недействительно.
- Оба автоматических способа не ждут просмотра или Approve: публикация после проверок.
- Концепция, метаданные и счётчики лежат в существующем JSON задания. PNG хранится
  через `MemeAssets` в локальном `LINKEDIN_POST_DATA_DIR/meme-assets`, не в Noco attachment.
  Это заменяемый файловый адаптер; при переносе backend нужен backup Noco и этого каталога.
  API выдаёт PNG только авторизованному клиенту с `no-store`, без публичной файловой папки.
- История до 10 готовых мемов передаётся модели; точный повтор сцены или подписи отмечается
  предупреждением, но не останавливает публикацию с мемом.
  Закрытие окна и restart не разрешают повтор потенциально выполненной генерации.

Notion в runtime не используется.
