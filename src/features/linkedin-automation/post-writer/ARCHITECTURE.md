# LinkedIn Post Writer

## Цель

Менеджер вручную запускает процесс одной кнопкой. После запуска система автоматически создаёт английский пост для выбранного ученика, проверяет его и при разрешённом режиме публикует в LinkedIn.

Есть два режима:

- `approval_required` — публикация после подтверждения менеджера;
- `automatic` — публикация сразу после успешных проверок.

По умолчанию используется режим с подтверждением.

## Последовательность работы

1. Менеджер выбирает ученика, режим и нажимает `Создать пост`.
2. Backend получает из NocoDB профиль, опыт, стек и историю публикаций ученика и собирает единый контекст для модели.
3. OpenAI предлагает 3–5 тем.
4. Backend исключает повторы и выбирает лучшую тему.
5. OpenAI пишет пост только на основе подтверждённых фактов.
6. Backend проверяет факты, язык, структуру и стиль. Допустимо не более двух исправлений.
7. Готовый текст и результаты проверок сохраняются в NocoDB.
8. `approval_required` ждёт подтверждения менеджера; `automatic` продолжает без паузы.
9. Подтверждённый или автоматический пост отправляется в Unipile.
10. Backend проверяет, что пост появился в LinkedIn, и сохраняет его ID и ссылку.

Повторный клик не создаёт второй активный запуск. В режиме `automatic` после клика участие менеджера не требуется, пока не возникнет неопределённость.

```text
ручной запуск
  -> данные ученика
  -> 3–5 тем
  -> выбор темы
  -> текст
  -> проверка
  -> подтверждение или публикация
  -> проверка результата
```

## Ответственность компонентов

| Компонент | Что делает |
| --- | --- |
| Backend | Управляет процессом и принимает все решения |
| NocoDB | Хранит настройки, запуски, версии текста и историю постов |
| OpenAI | Предлагает темы, пишет текст и исправляет замечания |
| Unipile | Публикует пост и возвращает данные результата |
| Web Console | Запускает процесс, показывает текст и даёт управление |

Frontend не обращается к NocoDB, OpenAI или Unipile напрямую. OpenAI и Unipile не являются источниками истины.

## Правила контента

Требования к выбору темы, тексту, проверке фактов и мемам описаны в [CONTENT_POLICY.md](./CONTENT_POLICY.md). Если контент не проходит эти правила после двух исправлений, запуск получает статус `manual_review`.

## Режимы публикации

### С подтверждением

Менеджер видит тему, текст и результаты проверок.

- `Approve` разрешает публикацию текущей версии.
- `Reject` завершает запуск без публикации.
- Изменение текста отменяет прежнее подтверждение.

### Полный автомат

Пост публикуется без участия менеджера только после всех проверок. Любая неопределённость переводит запуск на ручную проверку.

## Защита от дублей

Перед публикацией backend проверяет аккаунт ученика, Stop и отсутствие такого поста в истории.

Затем система:

1. Блокирует другие операции записи для этого LinkedIn-аккаунта.
2. Резервирует публикацию по `runId + contentHash`.
3. Выполняет один POST через Unipile.
4. Проверяет результат чтением LinkedIn.

При timeout, `5xx` или неподтверждённом результате запуск получает `uncertain`. POST вслепую не повторяется.

## Данные NocoDB

Нужны три логические сущности:

- `linkedin_post_settings` — режим по умолчанию и доступность функции;
- `linkedin_post_runs` — снимок контекста, варианты тем, версии текста, проверки, подтверждение, план лайков и состояние;
- `linkedin_post_history` — сигнатура темы, опубликованный текст, `contentHash`, post ID, ссылка и подтверждённые лайки.

Для одного ученика разрешён только один активный запуск. В MVP `contentHash` считается по тексту. После добавления мемов он объединяет хэш текста и хэш изображения.

## Состояния

```text
generating -> validating -> awaiting_approval | publishing -> published
```

Дополнительные состояния: `blocked`, `manual_review`, `rejected`, `stopped`, `failed`, `uncertain`.

После MVP добавляются `researching_meme`, `generating_meme`, `validating_meme`, `engagement_pending`, `engagement_running` и `engagement_partial`.

## Web Console

В консоли нужны:

- выбор ученика и режима;
- кнопка `Создать пост`;
- текущая стадия, тема, текст и результаты проверок;
- кнопки `Approve`, `Reject` и `Stop`;
- история запусков и ссылка на опубликованный пост.

## Границы MVP

В MVP входят ручной запуск, автоматический выбор темы, создание текста, проверки, два режима и публикация текстового поста.

Расписание, Notion и заранее подготовленные идеи не используются.

## После MVP

Следующий этап — автоматическое создание актуального профессионального мема под выбранную тему:

1. Найти актуальные узнаваемые форматы через отдельный search-адаптер.
2. Сформировать несколько концепций и исключить повторы последних 10 мемов ученика.
3. Сгенерировать и проверить один лучший вариант.
4. Сохранить файл в NocoDB как attachment вместе с alt text, хэшем и сигнатурой шаблона.
5. Подтвердить или автоматически опубликовать текст и мем одной версией.

Поиск используется для выбора актуальной концепции, а не как источник готового файла. Если безопасного узнаваемого шаблона нет, генератор создаёт оригинальную визуальную метафору. Изменение текста или картинки отменяет прежнее подтверждение.

### Обязательные лайки

После подтверждения публикации система автоматически ставит лайки с других подключённых аккаунтов учеников:

1. Один раз выбирает случайную цель: 6 или 7 лайков.
2. Выбирает столько же разных подключённых аккаунтов, исключая автора и уже поставивших лайк.
3. Ставит лайки последовательно со случайной паузой от 5 до 90 секунд между фактическими операциями.
4. Для каждого аккаунта получает общий operation gate и после mutation проверяет результат чтением.
5. Сохраняет выбранные аккаунты, попытки, подтверждённые лайки и время операций в NocoDB.

Restart продолжает только незавершённую часть сохранённого плана. Повторный лайк тем же аккаунтом запрещён. Неопределённый результат приостанавливает новые лайки до read-back; замена аккаунта разрешена только после подтверждённой ошибки. Stop сразу запрещает новые операции.

Запуск получает итоговый статус `completed` только после подтверждения целевого числа лайков. Если доступных подключённых аккаунтов меньше шести, публикация остаётся успешной, а поддержка получает `engagement_partial` с точным недобором.

## Проверка реализации

Тесты должны подтвердить:

- отсутствие повторов тем и публикаций;
- блокировку неподтверждённых фактов;
- ограничение исправлений двумя попытками;
- запрет публикации до `Approve` в режиме подтверждения;
- автоматическую публикацию только проверенного текста;
- отсутствие повторного POST после Stop, restart или неопределённого результата.
- выбор 6 или 7 уникальных аккаунтов для лайков после публикации;
- интервалы 5–90 секунд и отсутствие повторных лайков после restart;
- `engagement_partial`, если подключённых аккаунтов недостаточно.

Автоматические тесты используют mock-адаптеры. Первая live-публикация выполняется отдельно после явного разрешения.
