# Лента: накопление, отбор и 5 лайков + 1 комментарий

Локальная реализация для оркестратора. Команды на Node 24.20.0:

```sh
npm run linkedin:feed:test
npm run linkedin:feed:mock
```

## Контракт

`createFeedRun` получает ID прогона, подключённый аккаунт, подтверждённый ID
владельца, часы и список постов, запрещённых историей предыдущих отправок.
`stepFeedRun` получает сохранённый прогон, функции чтения/записи, модель,
адаптер Unipile, часы, random, Stop и проверку актуальности владельца исполнения.
Возвращает новое сохранённое состояние с этапом, сроком продолжения и причиной.
Исполнитель не создаёт таймеров, не читает ENV и не запускает фоновые процессы.

1. Для каждой новой порции случайно выбирает **30–120 карточек включительно**.
   Выбранный размер сохраняется до запроса. За один HTTP-запрос — не больше 100:
   например, порция 116 читается как 100 + 16 с паузой и сохранённым cursor.
   Остаток сохраняется; выбор постов начинается после получения порции или конца ленты.
   Повтор после ошибки использует тот же размер и cursor.
   Провайдер может вернуть меньше — offset увеличивается на
   фактически полученное количество. Сохраняет ID, тексты, признаки рекламы,
   доступности действий и существующей реакции, token и offset до оценки моделью.
2. Оценивает только ещё не оценённые карточки, пакетами до 20 с сохранением каждого
   результата, без повторного чтения LinkedIn. Профессиональная тема может быть
   любой: стек ученика не участвует. Реклама, спам, пустые и неоднозначные карточки
   исключаются. Тексты постов передаются модели как недоверенные данные.
3. Если нет пяти кандидатов и одного доступного для комментария, читает следующую
   порцию по сохранённой позиции. Старые карточки и оценки сохраняются, участвуют
   в общем выборе и повторно не запрашиваются. Предел — четыре HTTP-страницы / 400
   карточек; при нехватке результат частичный. Чтение ограничено шестью попытками
   и 30 минутами. После утраты результата незавершённого чтения — явная остановка,
   поскольку потерянный ответ мог содержать длинный Retry-After.
4. Сохраняет окончательный выбор до любых действий. Для каждого выбранного поста
   получает V2 ID и актуальные права через GET с native `activity:ID`/`ugcPost:ID`.
   Изменённый текст оценивает заново. Собственные, уже лайкнутые, недоступные или
   повторно разрешившиеся в тот же V2 ID посты пропускает с причиной.
5. Готовит один короткий комментарий под одним из пяти. Без выдуманного личного
   опыта, рекламы, ссылок и общих похвал. Модель возвращает цитату-основание;
   проверяем наличие цитаты в тексте, длину и отсутствие ссылок.
   Внешние парные кавычки вокруг цитаты допустимы; само содержимое должно совпасть
   дословно. Штатное продолжение может заново подготовить отклонённый валидатором
   комментарий, только если попытки отправки ещё не было.
6. Сохраняет намерение перед каждым POST. За проход максимум пять разных целей
   лайка и одна цель комментария. Комментарий отправляется после подтверждённого
   лайка этой цели. После каждого действия выполняет чтение результата.

Все накопленные карточки остаются в состоянии как минимум до окончательного
выбора; текущий прототип сохраняет их и после него для проверки результата.
Он не хранит полный ответ провайдера, cookies, ключи, заголовки или изображения.
Старые сеансы без поля randomPageSize продолжаются с прежним фиксированным размером;
read-only сеансы без поля cards остаются совместимы с исполнителем чтения.

## Паузы, сбои и журнал

Между действиями сохраняется случайная пауза 60–120 секунд; общая очередь аккаунта
учитывает прошедшее время, не прибавляя вторую полную паузу. Размер порции и пауза
выбираются независимо. Классификация и выбор постов не отменяют паузу перед следующим
обращением, а после подтверждения действия сохраняется пауза перед следующим.
Сам шаг не спит, ожидание возвращается оркестратору и не удерживает аккаунт.
Внешние обращения идут через существующий HTTP-клиент и установленную request
policy. Только строго ограниченный Raw GET домашней ленты классифицируется как
чтение; произвольные Raw POST остаются изменяющими запросами.

429 сохраняет абсолютный срок Unipile, без его сокращения или повторного сложения.
Standalone fallback чтения — два часа, 5xx/timeout — пять минут. В рабочей сборке
приоритет имеет общий сохранённый срок request policy. После неопределённой
отправки не повторяем POST: сохраняем ID комментария, если он известен, и
проверяем конкретное действие. Без ID подтверждаем только единственное собственное
совпадение по тексту и времени в полном стабильном списке комментариев этого поста.
Через 20 минут неподтверждённое действие остаётся unknown, остальные могут
продолжиться. Неизвестный комментарий сохраняет единственное место комментария.
Срок всего прохода с действиями — один час, без бесконечных повторов.
Последняя успешная проверка сразу сохраняет итог прохода, включая частичный результат.
Пауза нужна перед следующим запросом, а не перед завершением; уже подтверждённый
результат не должен превращаться в остановку из-за истечения часа во время такой паузы.
Общие паузы аккаунта и ограничения провайдера при завершении не сбрасываются.

Stop сохраняет исход начатого запроса и прекращает новые обращения. Ошибка
сохранения не маскируется как ошибка Unipile и запрещает следующий POST.
Состояние содержит этап, HTTP-статус и безопасный код ошибки конкретного действия;
`feedRunSummary` возвращает карточки, страницы, подтверждённые лайки/комментарии,
пропуски и неизвестные результаты. Частичный результат не обозначается успехом 5/1.

## Состав и границы проверки

- `home-feed.mts` — Raw GET ленты и нормализация карточек.
- `session.mts` — сохранённая пагинация.
- `selection.mts` — пакетная оценка, выбор и подготовка комментария; модель внедряется.
- `run.mts` — последовательные безопасные шаги одного прохода.
- `managed.mts` — шаг, Stop и продолжение в существующем оркестраторе; состояние
  и этапы сохраняются вместе с заданием в SQL, модель уступает account gate.
- `model.mts` — Responses API с отдельными инструкциями, строгой схемой и без tools.
- `feed-actions.mts` — стандартные Unipile V2 GET/like/top-level comment и сверка.
- `demo.mts` — сборка реальных модулей с файловым сохранением, общей очередью,
  подставными сетью, моделью и часами. Между шагами состояние перечитывается с диска.

Mock-демо с управляемым random: сначала 75 карточек, затем ещё 75; 5 лайков + 1 комментарий;
19 запросов = 2 страницы + 5 получений V2 ID + 5 лайков + 5 проверок лайков +
комментарий + его проверка. При достаточной первой странице этот сценарий требует
18 запросов. Ошибки и пагинация проверки комментариев могут увеличить число.
Это подсчёт конкретного mock-сценария, не измерение живого прохода.

Регрессии проверяют дозагрузку, рестарт, неполный выбор, рекламу, смену содержимого,
уже стоящие лайки, отказ модели, отказ сохранения до/после POST, 429, 500, Stop,
приоритет известного ID, старые/неоднозначные комментарии и отсутствие повторов.

Фича зарегистрирована в локальном коде календаря и backend как «Лента: 5 лайков +
1 комментарий», не более одного прохода в сутки. Используется прежняя общая очередь.
Состояние хранится в JSON существующего SQL-задания, новая таблица не нужна.
История начатых действий берётся из предыдущих заданий того же аккаунта, включая
остановленные и неподтверждённые; смена дня не сбрасывает защиту от дублей.
Используется существующая настройка модели комментариев с fallback на настройку
модели профиля. В журнале сохраняются ученик, аккаунт, этап и счётчики.
Наличие настройки модели проверяется до первого запроса ленты. Ошибки чтения и модели
сохраняют источник и HTTP-статус в общем журнале. Консоль получает компактные счётчики,
а не содержимое кэша; полное состояние восстановления остаётся в SQL.
Продолжение проверяет срок ленты и допустимость восстановления чтения до изменения
задания. Истекший срок и потерянный ответ чтения запрещают повторный запуск того же шага.
Не следует запускать `run.mts` отдельным живым процессом в обход этих зависимостей.
Проверка на mock не подтверждает качество модели и реальные отправки LinkedIn.
Живая SQL, расписание, ENV и работающая консоль этой локальной реализацией не изменены.

## Контракт провайдера

- [V2: native ID разрешён для GET поста](https://developer.unipile.com/v2.0/docs/linkedin-retrieve-posts.md)
- [V2: реакции](https://developer.unipile.com/v2.0/docs/linkedin-manage-post-reactions)
- [V2: комментарии](https://developer.unipile.com/v2.0/docs/linkedin-manage-post-comments)

Query ID Raw API может устареть: при ошибке формата/GraphQL нет перебора запросов.
Ошибка GraphQL сразу переводит весь проход в «нужна помощь». Журнал сохраняет
безопасные метаданные ошибки (статус GraphQL, известный тип, превышенный размер),
не подменяя ими HTTP 200. После проверки причины штатное «Продолжить» повторяет
тот же сохранённый шаг чтения, сохраняя порцию, cursor, попытки и срок прохода.
Потерянный ответ после прерывания чтения так не возобновляется: его Retry-After неизвестен.
Живые проверки и ограничения размера порции фиксируются отдельно в local-artifacts;
mock не подтверждает, что LinkedIn вернёт весь запрошенный объём.
10.10.2026 на аккаунте Полы запросы 30 и 100 вернули соответственно 30 и 100 карточек;
120 вернул GraphQL `Too many elements requested (120)`. Поэтому транспорт ограничен
проверенными 100 карточками, а больший случайный объём разбивается на части.

11.10.2026 повторный живой проход Полы стартовал по временному расписанию и завершился
без ручного продолжения: 118 карточек (100 + 18), 5 подтверждённых лайков и 1 комментарий,
19 запросов, без ошибок HTTP, пересечений или повторных отправок. Временный слот удалён.
После прохода отдельно исправлена задержка финального статуса; эта правка проверена
регрессиями с управляемыми часами, повторные живые отправки ради неё не выполнялись.
