# Мост Octo

Мост соединяет основной бекенд на Render с Octo Desktop на компьютере владельца.
На ПК нужны Node.js 24+ и открытый Octo под владельцем VEULink. Локальный бекенд,
Docker и входящие порты не нужны; мост сам обращается к Render.

## Что входит в решение

- `agent.mjs` — проверяет владельца и закрытое состояние профиля, получает
  одноразовое разрешение и снимает пароль через локальный Octo API.
- `journal.mjs` — сохраняет результат и не допускает повторной мутации после сбоя.
- `cli.mjs`, `start.ps1` — запуск, опрос и штатная остановка.
- `src/features/octo-access/bridge/` на сервере — защищённая очередь и разрешения.
- Изменения Octo workflow/runtime — постановка задания и проверка подтверждения.

Отдельного сервера для моста нет. Серверная часть работает внутри обычного
бекенда, с прежним хранилищем. Публичные Console API и схема БД не меняются.
Папка старого локального стенда и облачные диагностические сравнения удалены.

## Настройка и запуск

Скопировать `config.example.json` в `bridge.config.json`, указать адрес основного
бекенда, `bridgeId`, случайный секрет и точный email владельца. Для пилота задать
`allowedProfileUuids`. `allowAllManagedProfiles: true` разрешает обрабатывать
задания всех управляемых приложением профилей без ручного добавления UUID.

На Render нужны соответствующие приватные переменные:

```text
OCTO_PASSWORD_CLEANUP=bridge
OCTO_BRIDGE_ID=<bridgeId>
OCTO_BRIDGE_SECRET=<secret>
OCTO_BRIDGE_OWNER_EMAIL=<email владельца>
```

Секрет — 32 случайных байта в base64url (43 символа). Не использовать `VITE_*`,
URL-параметры или клиентские Console-запросы. Пароли профилей мост получает
от бекенда; вручную вводить их в конфигурацию не требуется.

После публикации серверной части и настройки Render:

```powershell
node cli.mjs --check
./start.ps1 -Background
```

Проверка должна вернуть `{"ownerVerified":true,"backendReady":true}`.
Она проверяет авторизацию, лидерство и готовность истории, без мутаций профилей.
HTTP 200 с HTML кабинета означает, что маршрут моста ещё не опубликован.
Проверка может выполняться при уже работающем мосте.

Штатная остановка: `node cli.mjs --stop`. Текущая операция сначала завершается
и сохраняет результат. Автозапуск Windows не устанавливается автоматически.
Логи находятся в `.state/stdout.log` и `.state/stderr.log`.

Если владелец работает в отдельном локальном Octo, задать серверному процессу моста
`OCTO_BRIDGE_LOCAL_PORT=58889`. По умолчанию используется прежний порт 58888.
Адрес остаётся `127.0.0.1`; меняется только порт трёх прежних операций Desktop API.
Личность владельца, закрытое состояние профиля, разрешения бекенда и журнал проверяются
как прежде. Порт контейнера публиковать только на loopback. Гостевой Octo может работать
параллельно на стандартном порту; его сессию мост не меняет.

## Поведение

1. Выдача защищённого профиля остаётся на 120 секунд. При запуске клиента пароль
   не меняется; повторный запрос срок не продлевает.
2. По сроку бекенд возвращает приватную папку и исходные метаданные. Открытый
   браузер продолжает работу. Отключённый мост не мешает этому возврату.
3. После обычного закрытия и проверки непрерывной истории бекенд выдаёт задание.
   Force-stop или разрыв истории не разрешают снятие пароля.
4. Мост повторно проверяет владельца и отсутствие активного браузера на этом ПК,
   затем вызывает `DELETE /api/profiles/password` на `127.0.0.1:58888`.
5. Завершение требует сохранённого подтверждения операции и облачной проверки.
   Один флаг `has_user_password=false` недостаточен. Облачного fallback нет.

Мост не запускает/останавливает браузеры, не назначает новый пароль и не
восстанавливает автоматически ранее повреждённые профили. Dolphin не затрагивается.

## Сбои и перенос

`.state/journal.json` не содержит паролей профилей, но необходим для сверки операций.
Потерянное подтверждение повторно отправляется серверу; локальная мутация не
повторяется. Неопределённая запись блокируется для ручной сверки.
Нельзя удалять журнал, чтобы повторить операцию. После аварии оставшийся lock
снимают только после проверки завершения записанного PID, сохраняя сам журнал.

Для переноса остановить мост, завершить все выданные ему задания, скопировать
программу и конфигурацию. `.state` не переносить на другой ПК. Незавершённое
задание автоматически другому ПК не передаётся. Для другого бекенда нужен новый
журнал; предыдущий журнал сохраняется отдельно после завершения всех его заданий.

## Проверки

`npm test` в этой папке запускает автономные тесты без npm-зависимостей.
`npm run octo:bridge:test` из репозитория также проверяет сервер, два клиента через
три цикла, сроки, перезапуски и неопределённые записи.
После `npm run web:build` команда `npm run octo:console:e2e:mock` проверяет всю
цепочку от интерфейса до агента с mock Octo. Для установленного Chrome задать
`OCTO_E2E_BROWSER_CHANNEL=chrome`. Настоящие профили этот тест не открывает.
[Проверка второго ПК](../src/features/octo-access/archive-acceptance/README.md)
остаётся условием выпуска: свежий ПК должен впервые открыть новый расходный
профиль без пароля и прочитать сохранённые данные. ПК, выполнявший снятие пароля,
не считается свежим устройством проверки. См. [результаты](TESTING.md).
