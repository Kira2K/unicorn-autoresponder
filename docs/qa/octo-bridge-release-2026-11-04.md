## Формы сохранены в master: временный пакет больше не нужен

Ранее формы ученика №204 были временной надстройкой из восьми исходников поверх
`347d282`. Архив восстановлен из присланного владельцем Base64; SHA256
`2e49c79c64624b314d781845bec1a3ed5a647beaf58b2750591d7f8b88863d56`
совпал с Render. Все восемь исходников сохранены приватно; ENV и данные учеников
в архив не входили.

Во время проверки владелец выпустил `855c8ecb` из PR #121: формы, диакритика и
несколько локаций стали обычным кодом Git для всех учеников. Затем #121 влит в
master как `8b8c536c05875507b7469e7152f4e81792223a5b`; его дерево совпадает с
уже работавшим `855c8ecb`. Ветка bridge актуализирована этим master.

Не возвращать `CLIENT_204_FORM_BUILD_PACKAGE_20261104` и старую команду применения
пакета: они ограничили бы новые формы прежним пилотом. Использовать существующую
сборку `npm install && npm run web:deploy-build`. Новые ENV и миграции для bridge
не требуются. Конфигурация Render в рамках подготовки не менялась.

## Порядок установки

1. Дождаться Live у backend после merge #121. Перед следующим выпуском проверить
   текущие deploy ID и обычное завершение активных выдач. Не force-stop.
2. Влить актуализированный #119 в master. Сначала выпустить backend и проверить
   bridge health. Если merge пропущен автодеплоем из-за `[skip render]`, выбрать
   Manual Deploy → Deploy latest commit у `Very Evil Unicorn`.
3. Убедиться, что worker-PR влит в его исходную ветку. На `unicorn-octo-owner`
   выбрать Manual Deploy нужного commit. Контекст `deploy/octo-render`, Dockerfile,
   секретные файлы, режим worker и диск `/var/data` сохраняются.
4. Проверить владельца/версию, журналы и один отдельно разрешённый расходный цикл.
   Новые логи содержат request ID, статусы, категории ответа и причины транспорта.
5. Не удалять `.state`/journal, не пересоздавать worker и не переносить журнал с ПК.

## Откат

Откатывать сначала worker, затем при необходимости Console. Сначала дождаться
завершения текущих операций/подтверждений. Не восстанавливать старую копию journal,
Octo cache или SQL: это может повторить уже выполненную внешнюю запись.

В Render: открыть Deploys сервиса, выбрать указанный успешный deploy и Rollback.
API: `POST /v1/services/{serviceId}/rollback`, JSON `{ "deployId": "..." }`.
Сам rollback не выполнялся. Наличие GitHub ADMIN и доступ к Render API подтверждены;
запись через API без реального отката повторно не проверялась.

Render может использовать сохранённый artifact, только пока он хранится по правилам
workspace. Если он недоступен, точный commit остаётся в Git; пересборка worker зависит
от доступности закреплённых по SHA256 Node/Octo-downloads. Откат artifact предпочтительнее.
Диск сохраняет текущее состояние. Dashboard rollback выключает autodeploy, API rollback
его не выключает — после отката не запускать повторный выпуск ошибочной версии.

Источники: [Render rollbacks](https://render.com/docs/rollbacks),
[rollback API](https://api-docs.render.com/reference/rollback-deploy).

- Точный старый agent/journal из commit `4194dd8` открыл журналы нового агента.
- `received`: разрешение получено повторно, ровно один clear.
- `executing` без подтверждения: ноль clear, результат остаётся uncertain.

ноль cloud clear; cleanup завершён. После актуализации сравнивается всё дерево
продуктовых исходников с этой проверенной комбинацией.
