## Важная зависимость текущей сборки Console

В рабочем сервисе применяется существующий временный пакет восьми файлов форм для
ученика №204: `CLIENT_204_FORM_BUILD_PACKAGE_20261104`. Его build-проверка привязана
к старому commit и хешам исходников. Прямой выпуск нового commit с прежним пакетом
будет отклонён. Не удалять эту надстройку и не терять её изменения.

Перед ручным выпуском пакет надо перенести трёхсторонним merge на ТОЧНЫЙ commit,
который будет развёрнут, и проверить сборку. Для feature commit подготовка хранится
приватно вне Git. После squash/merge SHA изменится — пакет нужно пересобрать на
новый SHA. В Git этот PR содержит только bridge-изменения; чужие формы сюда не включены.
Конфигурация Render в рамках подготовки не меняется.

## Порядок установки

1. Дождаться обычного закрытия активных профилей и завершения выдач. Не force-stop.
2. Актуализировать существующий пакет сборки Console на точный commit выпуска,
   сохранив его изменения. Сначала выпустить backend; проверить bridge health.
3. Убедиться, что worker-PR влит в его исходную ветку. На `unicorn-octo-owner`
   выбрать Manual Deploy нужного commit. Контекст `deploy/octo-render`, Dockerfile,
   секретные файлы, режим worker и диск `/var/data` сохраняются.
4. Проверить владельца/версию, журналы и один отдельно разрешённый расходный цикл.
   Новые логи содержат request ID, статусы, категории ответа и причины транспорта.
5. Не удалять `.state`/journal, не пересоздавать worker и не переносить журнал с ПК.

## Откат

Откатывать сначала worker, затем при необходимости Console. Сначала дождаться
завершения текущих операций/подтверждений. Не восстанавливать старую копию journal,
Octo cache или SQL: это может повторить уже выполненную внешнюю запись.

В Render: открыть Deploys сервиса, выбрать указанный успешный deploy и Rollback.
API: `POST /v1/services/{serviceId}/rollback`, JSON `{ "deployId": "..." }`.
Сам rollback не выполнялся. Наличие GitHub ADMIN и доступ к Render API подтверждены;
запись через API без реального отката повторно не проверялась.

Render может использовать сохранённый artifact, только пока он хранится по правилам
workspace. Если он недоступен, точный commit остаётся в Git; пересборка worker зависит
от доступности закреплённых по SHA256 Node/Octo-downloads. Откат artifact предпочтительнее.
Диск сохраняет текущее состояние. Dashboard rollback выключает autodeploy, API rollback
его не выключает — после отката не запускать повторный выпуск ошибочной версии.

Источники: [Render rollbacks](https://render.com/docs/rollbacks),
[rollback API](https://api-docs.render.com/reference/rollback-deploy).
