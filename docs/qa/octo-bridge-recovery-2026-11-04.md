# Восстановление bridge после потерянного разрешения и отчёты об ошибках

Ветка: `fix/octo-bridge-recovery`, актуализирована на master `8b8c536` после #121.

## Поведение

- Потерянный, невалидный или HTML-ответ `/authorize` оставляет локальную запись в `received`: Desktop DELETE ещё не выполнялся. Запрос разрешения безопасно повторяется с тем же grant ID и устройством, с задержкой до 30 секунд.
- Backend при повторе заново проверяет закрытие, папку, метаданные, историю, отсутствие результата и актуальность версии. Повтор не меняет первоначальное время авторизации. Чужое устройство и заменённая выдача отклоняются.
- Стадия `executing` записывается до Desktop DELETE. Неизвестный результат уже отправленной записи по-прежнему не повторяется; один облачный флаг не считается подтверждением. Потерянное подтверждение доставки результата повторяется без нового DELETE.
- Старые `uncertain`-записи автоматически не восстанавливаются и не переписываются.
- Логи агента и backend коррелируются по request ID и grant ID. Сохраняются этап, время, длительность, HTTP-статус, категория ответа, безопасный серверный код и категория транспортного сбоя. Пароли, прокси, Authorization и сырые тела не попадают в логи.
- Через общий `sendOne` / `VEU_SUPPORT_BOT` отправляется один отчёт в `-1003187558078` для заблокированной bridge-выдачи либо ожидания очистки больше двух минут. В сообщении — ученик, стек, профиль, операция и код ошибки.
- Попытка Telegram фиксируется CAS-записью в существующем JSON выдачи до отправки; затем сохраняется message ID либо состояние ошибки. Параллельный проигравший обработчик, перезапуск и потеря подтверждения не создают повторной отправки. Сбой Telegram не отменяет завершённую очистку и не останавливает другие профили.

## Выпуск

Миграция, новые переменные окружения и UI-изменения не нужны. Сначала выпустить backend, затем отдельно обновить реально работающий bridge-agent, сохранив конфигурацию и `.state`. Не удалять журнал и не повторять записи с неизвестным результатом. Для агента на отдельном Render-сервисе одного выпуска Console недостаточно.

В рамках разработки рабочая БД, реальные Octo-профили, Telegram-сообщения и deployment не изменялись. Подготовка публикации и отката описана в [порядке выпуска](octo-bridge-release-2026-11-04.md).
