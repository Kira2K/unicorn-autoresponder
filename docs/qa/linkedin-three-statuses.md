# Заявки LinkedIn: три статуса и две доставки

## Результат

«Не начата» и «блок» остаются открытыми. «Сделана экспертом» окончательно завершает заявку.
Денис сохраняет результат и проверенный прокси, затем выбирает этот статус. После успешного ответа
заявка исчезает из его рабочего списка, а ученик получает готовый LinkedIn и доступ к Octo.
Повторный запрос завершения не меняет версию и не запускает новый цикл или отправку.
Завершённую заявку нельзя открыть заново; следующий аккаунт оформляется новой заявкой после бана.

В одной SQL-транзакции завершаются заявка и локальный цикл LinkLab: новый account ID, статус «Новый»,
прогресс 0, ревизия -1; прежняя история, CRM ID, EN CV и физическая прокси-пауза сохраняются.
Дата `linkedin_account_cycles.applied_at` определяет начало 30-дневного прогрева.
Существующая логика CRM-команд остаётся прежней, её post-commit hook перенесён на окончательное
завершение Денисом. Неопределённый commit не разрешает повторять внешнюю CRM-команду.
`isUnsyncedWithCRM` не сбрасывается.

## Доставка

В `noco.linkedin_cycle_notifications` две независимые записи на новую завершённую заявку:

| recipient | Назначение | Содержимое |
| --- | --- | --- |
| reports | `-1003187558078` | Готовый LinkedIn / новый цикл, имя, стек, номер, URL; в конце `@juliafeels fyi`. |
| student | Учебный чат ученика | Поздравление, реквизиты в кабинете, месяц без входов, затем только Octo, без 2FA и смены пароля. |

Учебный чат: непустой `secured_general_chat_id`, иначе `telegram_general_chat_id`. ID фиксируется
в транзакции завершения и не заменяется другим адресатом при ошибке. Если чата нет, запись ученику
сразу получает `failed / recipient_missing`; отчёт остаётся доступным для отправки.
Текст ученику — HTML с обычными переводами строк, абзацами и маркированными пунктами; секретов нет.

Отправка через существующий `VEU_SUPPORT_BOT` / `sendOne` после commit. Отдельный status-report
для финального перехода отключён. У открытых переходов и подключения своего LinkedIn прежние
уведомления и теги сохраняются. Failed/uncertain не повторяются; просроченная attempting становится
uncertain. Две записи можно независимо получить через `FOR UPDATE SKIP LOCKED`.

Admin GET detail возвращает `notification.deliveries[]`: recipient, chatId, state, messageId/errorCode.
Админская вкладка показывает результаты доставок чтением. Старый POST `/:id/confirm` удалён.

## Порядок установки

Эти команды здесь только документированы. Рабочая БД, реальные сообщения и Render при подготовке PR не меняются.

1. Сделать штатную резервную копию. Проверить установленность прежних миграций:
   LinkLab `001`–`006`, creation-tasks `001`–`003` и используемых миграций intake.
2. Остановить все старые Console writers/dispatchers, включая локальные backend, использующие ту же БД.
   Не допускать работы старого dispatcher с двухполучательным журналом: он не знает нового назначения.
3. В checkout этого PR, с конфигурацией оператора, которому разрешён `SET ROLE unicorn_noco_copy_owner`,
   выполнить dry-run:

   ```powershell
   node --env-file-if-exists=.env src/features/linkedin-automation/creation-tasks/migrate-completion.mts --dry-run
   ```

4. Если получен `linkedin_pending_expert_tasks`, остановиться: CLI выводит номера старых
   «сделана экспертом» без завершённого цикла. Не завершать их автоматически и не обходить проверку.
5. После успешного dry-run применить ту же миграцию:

   ```powershell
   node --env-file-if-exists=.env src/features/linkedin-automation/creation-tasks/migrate-completion.mts --apply
   ```

6. Выпустить backend и frontend из одного commit. Новый backend проверяет наличие `recipient/chat_id`
   и не применяет DDL при запуске. Прежние права SELECT/UPDATE таблицы журнала сохраняются.
7. Проверить открытые заявки, read-only историю и журнал доставок. Реальный E2E и реальные сообщения
   запускать отдельно после разрешения на рабочие тестовые записи.

SQL `004-three-statuses.up.sql` транзакционно переименовывает прежнее «выполнение подтверждено».
Только для этого переименования отключены три конкретных бизнес-триггера; версии, даты,
LinkLab, аккаунты и ранее сохранённые результаты доставки остаются прежними. Новые события ученикам
по истории не создаются. Установка повторяема. Не запускать старые schema installers поверх новой схемы.
При ошибке до commit всё откатывается; после новых завершений исправлять вперёд, не запускать старую
версию против новой схемы и не удалять журнал/ledger для «отката».

## Проверка

Проверено локально 4 ноября 2026: 132 backend/Telegram-теста, 11 actual PostgreSQL checks и оба UI-теста
прошли. Четыре SQL-теста, пропущенные в общем mock-запуске без конфигурации БД, отдельно выполнены
на изолированном PostgreSQL без пропусков. Полный mock E2E двух регистраций и отдельный mock E2E
консоли Дениса прошли. TypeScript, production build и проверка diff прошли; стандартное предупреждение
сборки о размере bundle остаётся. Отдельный реальный CRM-handler не запускался.
Существующий mock E2E гостевого доступа Octo также прошёл: два пользователя, три цикла,
шесть bridge-clear, ноль cloud-clear, cleanup после обычного закрытия. Это не live-проверка Octo.

Все проверки используют изолированный PostgreSQL или mock-адаптеры. Подробные результаты
фиксируются в описании PR. Живое завершение и фактическая Telegram-доставка этим выпуском тестов не заявляются.

- SQL: отказ на ожидающей заявке с номером; dry-run rollback; историческое переименование и повторная
  установка без смены версий/дат/циклов/receipt; отсутствие старых профилей не мешает миграции.
- SQL: атомарность завершения, ограниченная роль, чужие привязки, два цикла с одним набором профилей,
  сохранение CRM ID/CV/прокси-паузы/флага синхронизации, запоздалые CRM-результаты.
- SQL/backend: незаполненный результат, активный доступ, старые/подменённые прокси, CAS и повторные запросы.
- Telegram mock: два назначения, формат текста, отсутствие тега в отчёте, отсутствие учебного чата,
  независимые отказы и неопределённые результаты без повторной отправки.
- UI/mock E2E: форма ученика → работа Дениса → готовый LinkedIn → бан → повторная заявка → второе
  завершение; обновление без перезагрузки и после неё, отсутствие дублей профилей и четыре mock-доставки.
- Дополнительно: связанные backend/UI/Telegram-регрессии, проверка типов и production build.
