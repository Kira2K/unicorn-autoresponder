# Подключение существующего LinkedIn через Octo

## Что меняется

Только ученический сценарий «У меня есть LinkedIn» получает четыре шага:
сохранить URL/логин/пароль → проверить свой прокси → войти через EN Octo →
подтвердить подключение. Раздел LinkedIn по умолчанию открыт, четыре шага
свёрнуты независимо. Сворачивание не размонтирует формы и не стирает поля.

Черновое сохранение не создаёт заявку эксперту и не включает LinkLab/уведомление.
После готового Octo, выданного доступа и подтверждения входа успешный ответ
`saved: true` с ID аккаунта показывает модалку «LinkedIn успешно подключён ✅».
Пароль можно показать/скрыть; пустой сохранённый пароль сохраняет прежний.

Ручной ученический прокси проверяется одним HTTPS-запросом через подключение.
Нужны успешный ответ и IP; страна и репутация не блокируют этот сценарий.
Общий таймаут — 10 секунд, private/loopback gateway отклоняется до подключения.
При ошибке реквизиты остаются в форме. Fingerprint связывает проверку с точными
реквизитами; после сети повторно проверяются состояние и ревизия. Готовые
RU/EN-профили переиспользуются. Неопределённые внешние записи не повторяются.
Экспертный процесс Дениса и подбор NodeMaven не переводятся на этот checker.

«Меня забанили» сразу показывает текущий аккаунт в read-only истории со ссылкой
и логином, без пароля. При сохранении новой заявки он становится архивным.
«Отмена» откатывает только бан текущего действия по версии строки PostgreSQL
`xmin`. Более поздние изменения или новая заявка запрещают откат. Изначально
заблокированный аккаунт не разблокируется; неизвестный commit перечитывается.

## Совместимость с master

Сохраняются CRM-вызовы master после COMMIT бана и подтверждения замены.
**Отмена меняет только статус в Unicorn. Уже доставленный CRM-бан не отменяется
автоматически. CRM-команда `unban` запускает прогрев и в эту доработку не входит.**
При включённых CRM-командах ошибочный бан требует отдельной сверки на стороне CRM.

## Порядок установки

До запуска новой версии backend установить явную миграцию колонки
`linkedin_octo_connection_pending boolean NOT NULL DEFAULT false`:

```powershell
node --env-file=.env src/features/linkedin-automation/console-intake/migrate.mts --existing-connection
node --env-file=.env src/features/linkedin-automation/console-intake/migrate.mts --existing-connection --apply
```

Первая команда выполняет dry-run с ROLLBACK, вторая — применение. Соединение
оператора должно иметь существующее право SET ROLE `unicorn_noco_copy_owner`.
Startup выполняет проверки схемы без DDL. Миграция не изменяет прежние привязки,
не переподключает старые аккаунты, не воспроизводит handoff/уведомления. Сначала
миграция, затем backend/worker нового выпуска. Нужны Node 24.20.0 и `npm ci`:
SOCKS/HTTP CONNECT адаптеры объявлены прямыми зависимостями.

Эта подготовка PR не применяет рабочие миграции, не меняет ENV и не деплоит.

## Проверки

На дереве PR от master `06c63b0d…`: 109 целевых тестов прошли без пропусков,
изолированный SQL-набор прошёл, TypeScript и production build прошли. Оба
mock browser E2E прошли; Octo завершил 3 цикла для двух учеников, 6 cleanup,
0 cloud-clear. Окончательные store/connectivity проверки повторены после
уточнения CRM-совместимости и обезличивания фикстуры IP: 29/29.

Целевой unit/API набор включает intake, owner guards, отмену и неизвестный
commit, историю, startup, ручной checker, сохранение профилей, proxy validation
и сохранённые контракты CRM. Изолированный PostgreSQL проверяет SQL миграцию,
отмену по настоящему xmin и конфликт с изменением login без обновления timestamp.

Mock browser E2E проходит существующий/новый LinkedIn, бан/отмену/повторное
оформление, ошибки и модалку, перезагрузку, скрытые пароли, RU/Dolphin routing
и desktop/mobile. Отдельный Octo mock E2E проверяет access/cleanup циклы.
Типы и production Vite build проверяются на точном дереве PR.

Эти проверки не доказывают новую live-доставку Telegram/CRM или регистрацию
на внешних LinkedIn/Outlook. Учётные данные и операционные артефакты в Git не входят.
