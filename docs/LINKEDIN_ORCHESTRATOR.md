# Автоматизация LinkedIn

Календарь и обновлённый интерфейс из этой инструкции добавляются третьим PR.
На этом этапе доступны backend, API, миграция и диагностика.

Расписание запускается backend, независимо от открытой консоли. Код оркестратора
находится в `src/features/linkedin-automation/orchestrator`, SQL — в
`src/integrations/postgres/linkedin-automation`. Исполнение и проверки результатов
остаются в существующих фичах. Часы, случайность, хранилище и адаптеры передаются
через зависимости; модуль календаря не обращается к внешним сервисам.

## Работа в консоли

1. Открыть LinkedIn и отметить нужных учеников.
2. Развернуть «Расписание и журнал» → «Настроить выбранных».
3. Выбрать дни, интервалы и фичи. Время — МСК. Ночной интервал разделяется
   на два дня; пересечения запрещены. Можно скопировать день на другой день.
4. Включить автоматизацию и сохранить. Консоль покажет результат отдельно по
   каждому выбранному ученику. Копируется расписание первого выбранного ученика;
   дальнейшие изменения каждого ученика независимы.
5. Читать состояние, причину ожидания и журнал. «Журнал» у запуска отбирает его
   события, «Показать более ранние события» читает сохранённую историю.

«Свернуть» скрывает весь блок; «Свернуть автозапуски» — только список запусков.
Выбор сохраняется в этом браузере после перезагрузки. Это **не выключает** фичи.
Для остановки снять нужную фичу и сохранить либо нажать «Выключить выбранных».
Ручные задания при этом не отменяются. Отправленный запрос сначала проверяется,
следующий автоматический запрос не начинается.

Приглашения используют прежнюю дневную норму, а посты — прежний дневной ключ
и максимум один автоматический пост в сутки. Отзыв получает свежие ожидающие
приглашения и выбирает строго старше 14 суток, включая отправленные вручную.
Ручной отзыв по-прежнему требует подтверждения. Комментарии включаются флажком
хотя бы в одном слоте. Если включены посты, первый запуск ждёт подтверждённой
автоматической публикации (подходит и уже опубликованный сегодня пост). Задержки
в 10 минут нет. Без постов монитор запускается при включении автоматизации,
не ожидая часа начала слота. В неактивный день первый запуск ждёт активного дня.
Далее монитор работает весь день МСК, если на этот день есть **любой** слот,
включая дни без постов. В дни без слотов монитор на паузе. Когда другая задача
ученика готова к запуску или выполняется, комментарии уступают аккаунт: уже
отправленный ответ проверяется, новый не отправляется до освобождения аккаунта.
Ручные операции также защищены общей блокировкой аккаунта. Новая подтверждённая
публикация добавляется в два отслеживаемых поста без сброса состояния.
Обновляются 48-часовые сессии, сохраняются
лимиты 30 ответов за сессию и 7 в треде, история ответов и проверка неопределённых
результатов. Достижение лимита не сокращает первоначальные 48 часов.

Резерв длительности: максимум оценки оставшейся работы, p90 последних 20
завершённых запусков той же фичи/ученика и начального резерва, затем +30% и 10 минут.
Начальные резервы: приглашения 180, пост 30, отзыв 20 минут. Фоновый монитор
комментариев не занимает отдельный резерв слота и не участвует в случайных паузах.
Приглашения учитывают остаток нормы; отзыв — число подходящих приглашений,
максимальные штатные паузы и время проверки. Оценка отзыва кешируется на 5 минут;
список перед исполнением перечитывается. История постепенно уточняет резерв.
Оценка не гарантирует длительность внешнего сервиса. Начатая задача может
закончить после слота. Пропущенные дни не накапливаются в очередь.

Для одного ученика весь слот планируется как последовательность задач в порядке
выбранных фич. Сначала резервируется суммарное время работы; оставшееся время
случайно распределяется перед первой задачей, между задачами и после последней.
Паузы между задачами — минимум один такт планировщика (5 секунд); верхнего
фиксированного предела нет. Начала и паузы сохраняются в SQL и не меняются на
каждом тике или после перезапуска. При задержке предыдущей задачи следующая
ожидает её фактического завершения плюс сохранённую паузу. Если времени с резервом
уже не хватает, запуск пропускается до следующего разрешённого слота.
При изменении слота ранее сохранённые начала не перетасовываются: новые фичи
занимают оставшееся место после уже запланированных задач.

Разные ученики могут выполнять задания одновременно без общего лимита на их
количество. У одного аккаунта остаётся единая блокировка автоматических и ручных
операций. Очереди и ограничения запросов Unipile не изменены. Монитор комментариев
занимает блокировку на отдельную проверку; его активация считается завершённым
шагом расписания, а повторные проверки не отодвигают паузу следующей фичи.

Лимит задачи фиксируется при запуске: `max(2 × резерв, резерв + 30 минут)`.
Например, резерв поста 49 минут даёт лимит 98 минут, а резерв приглашений
4 ч 4 мин — 8 ч 8 мин. Дедлайн сохраняется в SQL и не продлевается перезапуском.
По достижении лимита оркестратор вызывает штатную остановку фичи; защита перед
каждой внешней записью также проверяет дедлайн, независимо от очередного тика.
Post Writer повторно проверяет его после ожидания в очереди Unipile, прямо перед
HTTP POST (публикация и лайк). Отказ до отправки не считается неопределённым POST.
Причина `task_time_limit` и дедлайн видны в журнале. Отправленный запрос сначала
проверяется: до освобождения аккаунта следующая задача не запускается. Таймаут
не затрагивает ручные задания или весь фоновый монитор комментариев.
Это безопасная остановка, а не принудительное убийство процесса: при зависшей
проверке результата аккаунт остаётся занят, другие ученики продолжают работу.

## Подготовка SQL и запуск

Используется Node 24.20.0 и существующий SQL-адаптер проекта. Этот документ
не запускает миграции или процессы. `unicorn_noco_copy` — рабочая база, несмотря
на название; не использовать её для тестов. Сначала проверить на отдельной
тестовой SQL. ENV и секреты в Git не добавляются.

Перед внедрением сохранить резервную копию SQL и файлов журнала отзывов.
На **хосте существующего исполнителя** указать `LINKEDIN_WITHDRAWAL_DATA_DIR`
с его действующими журналами (по умолчанию `storage/linkedin-invitation-withdrawal`).
Если журналы находятся на нескольких хостах, сначала собрать и сверить их;
не подменять их пустым каталогом. Остановить только LinkedIn-исполнители для
миграции: CLI требует эксклюзивную блокировку, которую держит новый SQL backend.
Иные сервисы эта команда не останавливает.

В отдельном процессе с реквизитами роли миграций выполнить:

```powershell
npm run linkedin:automation:migrate -- --apply --target=<HOST>:<PORT>/<DATABASE>
```

HOST/PORT/DATABASE должны точно совпадать с `APP_DB_POSTGRES_*` этого процесса.
Команда дополнительно проверяет разрешённое имя базы и существующий SQL-маркер,
создаёт только схему `linkedin_automation` и переносит журнал отзывов.
Исходные JSON-файлы не удаляются. Уже начатые попытки не затираются: конфликт
файлов и SQL блокирует импорт. Незавершённый импорт блокирует запуск.
После миграции роли приложения нужны USAGE на новую схему, SELECT/INSERT/UPDATE
на её таблицы и USAGE/SELECT на sequence журнала. Выдать права владельцем схемы
на конкретную роль приложения. CREATE/ALTER приложению не требуются.

Для первого запуска backend:

```ini
APP_DB=postgres
LINKEDIN_ORCHESTRATOR_ENABLED=true
LINKEDIN_ORCHESTRATOR_PREVIEW_ONLY=true
```

Остальные `APP_DB_POSTGRES_*` и реквизиты провайдеров — существующие настройки
выбранной среды. Они не меняются скриптом. Запуск обычный:

```powershell
npm run web:build
npm run web:start
```

Сначала посмотреть расписания в режиме preview: автоматические отправки
запрещены, ручные действия сохраняют прежнее поведение. Существующие расписания
Post Writer остаются прежними, пока ученик не включён в новом календаре.
После первого включения управление этим учеником закрепляется за оркестратором;
старый планировщик больше не создаёт ему задания, даже при выключении фичи.
Текущие задания и дневные ключи сохраняются.

Только после согласованной проверки одного ученика установить
`LINKEDIN_ORCHESTRATOR_PREVIEW_ONLY=false` и перезапустить выбранный backend.
Прежние `LINKEDIN_CONNECTION_WRITER_ENABLED` и `LINKEDIN_POST_WRITER_ENABLED`,
права аккаунтов и ограничения провайдеров остаются обязательными.

## Один исполнитель и восстановление

Постоянная advisory lock использует отдельное соединение. Два соединения пула
данных остаются доступны интерфейсу и операциям хранения; вместе с блокировкой
этот backend использует до трёх соединений SQL. Ключ блокировки относится только
к LinkedIn: другие SQL-транзакции его не запрашивают и не блокируются им.
Скрытые ручные панели учеников загружаются только после первого открытия.

Если проверка схемы оркестратора, переноса журнала или соединения блокировки
не прошла, остальная веб-консоль продолжает запуск. LinkedIn переходит в режим
без отправок и восстановления заданий; старые планировщики не включаются.
Причина доступна в API автоматизации (503) и в журнале запуска backend.
После устранения причины нужен перезапуск. Ошибки общей SQL-конфигурации,
маркера основной базы и генераторов ID по-прежнему прерывают запуск консоли.

Перед деплоем проверить суммарный лимит подключений и нагрузку общей SQL при
включённых HH, Telegram и консоли. Локальные проверки блокировки и mock-регрессии
не заменяют проверку ресурсов целевого сервера и общей квоты Unipile.

Все SQL backend **этой версии** берут одну PostgreSQL advisory lock, независимо
от флага календаря. Второй backend не выполняет изменяющие LinkedIn-операции.
Один аккаунт занят одной операцией; число параллельно работающих учеников
оркестратор не ограничивает. Лимиты провайдера сохраняются. Комментарии
занимают блокировку только на отдельную проверку. Ручные подключение аккаунта
и Profile Filler используют ту же границу исполнения.

**Старые версии не знают об этой блокировке.** Перед первым рабочим включением
нужно обновить конкурирующие LinkedIn backend или отключить в них исполнение.
Одна новая блокировка не защищает от старого процесса или внешнего скрипта.

Потеря БД/владения блокировкой запрещает следующие отправки. Для возвращения
утратившего блокировку исполнителя требуется перезапуск. Сначала проверяются
сохранённые задания и намерения; неоднозначные запросы не повторяются вслепую.
SIGINT/SIGTERM запрещает новые действия и даёт до 30 секунд на сохранение
результатов. После жёсткого завершения оставшиеся намерения проверяются при старте.

Удаление флага календаря после миграции переводит его в preview, но сохраняет SQL
журнал отзывов и владение расписаниями. Не откатывать бинарную версию на старый
код с файловым журналом до сверки новых SQL-попыток: это может потерять защиту
от повторов. Безопасная первая мера при проблеме — выключить выбранных учеников
или перейти в preview. Схему, события и историю не удалять.

## Журнал и проверка по запросу

SQL сохраняет запуск, ученика, фичу, этап, время, код результата/ошибки, счётчики,
HTTP-статус и время ожидания, если их передала фича. Связь с заданием фичи
сохраняется. Запись намерения обязательна **до** внешней записи; результат
проверяется и записывается после неё. Синхронные служебные логи фич сбрасываются
в SQL перед следующей внешней записью. Сбой журнала закрывает запись до
перезапуска; последний heartbeat позволяет увидеть недоступность исполнителя.

Raw-ответы провайдеров, токены, cookies, тексты резюме и произвольные сообщения
ошибок в диагностический API не попадают. Неизвестный безопасный код виден как
код, а не как выдуманная причина. При аварии процесса или БД точный последний
результат может быть неизвестен: это явно показано как устаревший heartbeat или
неопределённая отправка. Абсолютная гарантия записи после аппаратного сбоя не
обещается. Неопределённая отправка требует проверки, не повторного POST.

В первой версии события не очищаются автоматически; старые страницы доступны
после перезапуска и через несколько дней. Нужно включить схему
`linkedin_automation` в регулярный backup PostgreSQL и контролировать её размер.
История автоматических комментариев не удаляется 30-дневной очисткой, потому
что содержит защиту от повторных ответов.

Для диагностики без права управления:

1. Создать отдельный случайный `LINKEDIN_DIAGNOSTICS_TOKEN` длиной минимум 32
   символа и задать его на backend и машине, с которой читается статус.
2. На читающей машине задать `LINKEDIN_DIAGNOSTICS_URL=https://<backend>`.
3. Выполнить:

```powershell
npm run linkedin:automation:status
npm run linkedin:automation:status -- --account=203
npm run linkedin:automation:status -- --runKey=<KEY>
```

Это отдельный GET-клиент: он не запускает backend, планировщик и провайдеров.
Достаточно URL и токена; доступа к SQL/Unipile ему не нужно. Так агент может
проверять состояние по запросу пользователя, если endpoint доступен с его
машины. При недоступности сервера он сообщает недоступность, не «всё хорошо».
Постоянный внешний мониторинг отдельно не создаётся.

Административные API: GET `/api/admin/linkedin/automation`, GET
`/api/admin/linkedin/automation/diagnostics`, PUT `/api/admin/linkedin/automation/:account`,
POST `/api/admin/linkedin/automation/bulk`. Читающий токен принимается только
для GET; изменения требуют штатную admin-сессию и актуальную ревизию настроек.
Диагностика поддерживает `account`, `runKey`, `before`, `limit` (до 500).
Для закрытой SQL есть `npm run linkedin:automation:sql-status -- --account=203`:
команда использует реквизиты SQL из своего окружения и ничего не меняет.

## Локальные проверки

```powershell
npm run linkedin:automation:test
npm run typecheck
npm run web:build
npm run linkedin:automation:e2e
```

SQL-тест по умолчанию пропускается без `LINKEDIN_TEST_PG_BIN`. Если передать
каталог `bin` PostgreSQL 16 для Windows, тест сам создаёт временный кластер
на свободном loopback-порту, синтетические данные, проверяет конкурирующих
исполнителей, потерю соединения и перезапуск и останавливает этот кластер.
Рабочие реквизиты не загружаются. E2E использует mock backend и локальный
браузер, проверяет выбор нескольких учеников, журнал, выключение и сохранение
сворачивания. Это не является проверкой реальных отправок в LinkedIn.
